# Clumsy

A lightweight PDF viewer built on Tauri that also opens Markdown files. Releases are macOS-only today (15.4 or later, `bundle.macOS.minimumSystemVersion`); Windows and Linux are planned, so keep platform-specific code behind `platform.ts` / `cfg(target_os)` and wording platform-neutral. Tagline: "No tricks, no acrobatics." Avoid naming other companies' products (for example Adobe Acrobat) in the app, README, or store listings. Tauri 2 (Rust) shell, React 19 + TypeScript UI, pdf.js 6 for rendering and markup, markdown-it and CodeMirror 6 for Markdown. Sponsored by Texas Beard Company, the same branding used in TheAnnex and DutiHEHE.

Repo: https://github.com/ry4nolson/clumsy (public, MIT License). The local folder is still named `pdf-viewer`. The license covers code only: the Clumsy name and icon and the Texas Beard Company name and logos are excluded (see README).

## Commands

```bash
pnpm install
pnpm tauri dev                 # run the desktop app with hot reload
pnpm dev                       # browser-only UI at http://localhost:1420 (no file paths, menus, or recents)
pnpm test                      # vitest (tests/*.test.ts)
pnpm exec tsc --noEmit         # typecheck
cargo clippy --manifest-path src-tauri/Cargo.toml -- -D warnings
cargo test --manifest-path src-tauri/Cargo.toml --lib
pnpm tauri build --bundles app # local release build -> src-tauri/target/release/bundle/macos/Clumsy.app
pnpm licenses                  # regenerate public/third-party-licenses.txt (also runs as part of pnpm build)
```

- Node 20.19+ is required by Vite 8 (Node 22 recommended). pnpm is pinned through `packageManager` in `package.json`.
- Universal builds (`--target universal-apple-darwin`) need rustup's toolchain with `x86_64-apple-darwin` installed. Homebrew's `cargo` can't cross-compile, so put `~/.cargo/bin` first in `PATH` for those builds.

## Architecture notes

- **Tabs and panes.** `src/lib/workspace.ts` is the pure, tested model: a map of tabs plus an ordered list of panes (each with its tab order, active tab, and flex size) and the focused pane. Every open document mounts its own `DocumentTab` with its own pdf.js `PDFViewer`; never swap documents inside one viewer, because unsaved highlights and notes live in the viewer's editor layer. `PaneGrid` lays panes out as a CSS grid (row 1 tab strips, row 2 documents, 5px divider columns between panes) and renders every `DocumentTab` as a sibling in one keyed list, positioned by `gridColumn`. That is what lets a tab move between panes without remounting: only its column changes, so scroll, zoom, and unsaved markup survive. Inactive tabs stay laid out but hidden (`visibility: hidden` + `inert`); `display: none` would reset their scroll position. Hidden still intersects, so anything that renders on visibility must also check the tab is active. After `HIDDEN_RELEASE_MS` hidden, a tab destroys its finished page views (`releasePages`, the same thing pdf.js does when it evicts a page from its buffer; skipped while an editing mode is on) and `viewer.update()` redraws them when it's shown. Unmounting a viewer must call `viewer.setDocument(null)` before `partsRef` is cleared (it's in `usePdfViewer`'s cleanup, which runs before `DocumentTab`'s), and the viewer gets an `abortSignal`: otherwise pdf.js's editor UI manager keeps its window and document listeners and every closed tab stays in memory. App keeps per-tab `TabSnapshot`s (page, zoom, tool, modified, find state); the focused pane's active tab drives the toolbar, menus, and window title. Tab dragging and divider resizing are pointer-event based in `PaneGrid` (HTML5 drag and drop is unreliable in Tauri webviews); the divider has a widened invisible grab area. At most `MAX_PANES` (4) panes.
- **Document windows.** Every document window (label `main` or `doc-*`) runs the full `App` with its own workspace; `src/lib/documentWindows.ts` opens them, finds the window under a drop point, and hands tabs over; `useTabTransfer` drives it from the app. A live pdf.js document can't move between webviews, so moving a tab calls `saveDocument()` (unsaved markup is baked in), stashes the bytes in Rust (`stash_transfer` / `take_transfer`, raw IPC, taken once, at most 2 GiB held at a time), and the receiving window reopens them with the same page and zoom. A tab that arrives with unsaved changes keeps a `carriedChanges` flag so it still reads as edited until saved; undo history from before the move is lost. Each window builds its own app menu and calls `activate()` (`setAsAppMenu`) when it gains focus, because menu callbacks run in the window that built them. Don't give menu items fixed ids: Tauri routes menu clicks through one app-wide id → handler map, so a shared id sends every window's clicks to the newest window. Keyboard shortcuts hide the problem because the focused page handles them first. Rust tracks the last focused document window (`windows.rs`) and sends Finder-opened files there with `emit_to`, which is why `files-opened` is listened for per webview. Each window reports its open paths and unsaved document names to Rust (`report_documents`) whenever they change; opening a path another window already has focuses that window's tab instead (`document_window`, `show-document` event), so one file never has two writers in different windows. The default-app launch prompt only runs in `main`. Capabilities list `doc-*`. Tab tear-off is detected in `PaneGrid` when a drag ends outside the window; drops onto another window merge into its focused pane.
- **Start tabs.** Opening a file from a Start tab replaces that tab, like a browser's new-tab page. Opening a path that's already open anywhere switches to its tab, except Split Right, which deliberately opens a second copy. Closing the last tab in a pane removes the pane; closing the last tab overall leaves a Start tab.
- **Saving.** `pdfDocument.saveDocument()` writes markup and form values as an incremental update over the original bytes held by the worker, so repeated saves don't duplicate annotations. The Rust `write_pdf` command takes raw bytes with the path in a percent-encoded `x-path` header and writes atomically (temp file + rename, into the symlink's real target, keeping the original permissions), `.pdf` paths only. Each tab keeps the file's stamp (mtime + size) from when it was read; saving to the same path sends it as `x-expected-stamp`, and if the file changed on disk Rust refuses with `changed-on-disk` so the app can ask before overwriting. Saving returns the new stamp. Markdown tabs save their text through `write_markdown` (`.md`/`.markdown` only) with the same atomic write and stamp check. A path Rust only allowed for reading (a file opened from a Markdown link) answers `not-writable`, and Save falls back to a Save As dialog (`writeTo` in `useSaveDocument.ts`). A tab with `protection` encrypts its bytes on the way to disk (see Passwords).
- **External changes.** `useExternalChanges` polls `file_stamp` for each open file every 2 seconds while the window is visible, and right away when it gains focus. A tab reloads in place (same page, zoom, and scroll, via `viewState()`) only when `canReload` in `src/lib/externalChanges.ts` says so: the stamp changed, nothing is unsaved or carried over from another window, the draw or text tool isn't active (those can hold edits pdf.js hasn't committed yet), and no alt text, signature, or comment sheet is open (`sheetOpen` in the tab snapshot). Before swapping, the stamp must hold steady for 300 ms and a PDF's new bytes must end in `%%EOF`, so a file another program is still writing isn't loaded half-done. A Markdown tab has no tools, so it reloads whenever its text matches what was last saved and nothing was carried over; its new bytes only have to decode as UTF-8, and the view comes back on the same source line. Edited tabs are left alone; Save's changed-on-disk prompt covers them.
- **Page edits.** `src/lib/pageEdits.ts` does the structural work with `@cantoo/pdf-lib` (the maintained pdf-lib fork, which can also encrypt): reorder, delete, rotate, insert another PDF, extract, combine. The low-level page tree work lives in `src/lib/pdfStructure.ts`. pdf.js can't change a document's pages, so every page edit takes the current bytes from `viewer.save()` (unsaved markup is baked in, like moving a tab between windows), rewrites them, and swaps them into the tab as a new `source` with `carriedChanges: true`, keeping zoom and moving to the right page (`pageAfterEdit`). Every edit first flattens the page tree into one `/Pages` node, copying inherited `Resources`/`MediaBox`/`CropBox`/`Rotate` onto each page, and then just rewrites `/Kids`. Pages are found with `pageLeafRefs` and inherited values through a visited set, never pdf-lib's `getPages`/`getPageCount`/`traverse`/`getInheritableAttribute` on an unflattened tree, because those recurse without cycle checks and a page tree that lists itself or a `/Parent` loop (which pdf.js opens fine) overflows the stack; pruning fields likewise cuts a kid entry that points back at its own ancestor; pdf-lib's own `removePage`/`insertPage` corrupt the tree when every page moves and let inserted pages inherit a branch's rotation. Removing pages (delete, and extract, which removes everything else) also removes their annotations and form widgets, fields left with no widgets (and their `/CO` calculation-order entries), tagged-PDF structure elements whose content was all on those pages (`src/lib/pdfStructTree.ts`, so their `/Alt` and `/ActualText` go too, along with their `/IDTree` entries), links, bookmarks, and an `/OpenAction` that pointed at them (named destinations are resolved through `/Dests` and the `/Names` tree before they're pruned, since LaTeX and many other producers only use names), and named destinations, then nulls any other reference to them. Removing pages also drops XFA form data (pdf.js doesn't render it, and it keeps its own copy of every field value); other edits keep it, because a dynamic XFA form has nothing else. Structure elements reached through two parents are decided once, and an `OBJR` pointing at an annotation is judged by that annotation, not by the element's `/Pg`. Pages copied in from another file lose `/StructParents` so they don't collide with the target's structure tree. Before saving, `collectGarbage` drops every object the trailer can't reach and pdf-lib rewrites the whole file, so a deleted page's content is really gone and no earlier revision survives. That matters: people delete pages to remove private information. Inserted and combined pages are copied by copying the source's (flattened) page tree in one pass, so links between them point at the copies. Their form fields stop being fields, and the first file's fields keep working when combining. The current document is loaded with its version's password (or `""`, which opens owner-only files), so edits work on protected files and return plain bytes (see Passwords); files being inserted or combined are loaded with `""`, and one that needs a password is refused with a clear message. Page labels follow their pages: every edit except rotation reads the `/PageLabels` number tree (`src/lib/pdfPageLabels.ts`), maps each label to its page ref, and writes a fresh tree with `encodePageLabels` (`src/lib/pageLabels.ts`) that finds decimal, roman, and letter runs and falls back to a prefix-only range per page. Inserted and combined pages bring their own file's labels, or their new page number when that file has none. A file without labels never gains them from these edits. Pages > Page Labels… edits them directly: `PageLabelsDialog` (an in-window sheet rendered by `DocumentTab`, opened through `DocumentHandle.editPageLabels`) sends a `label` page action, and the `label` page edit rewrites the tree from `relabelRange`, so it's queued, undoable, and marks the tab edited like the others. The sheet starts on the current page's run (`numberingAt`, `runEnd`) or the selected pages, so its prefilled values change nothing until edited; ranges that leave every page with its own number delete `/PageLabels`.
- **Comparing documents.** A comparison is two tab ids held by `useComparison`; `workspace.ts` knows nothing about it. It ends when either tab closes, leaves the window, or both land in the same pane. `pdfText.ts` reads each page's `getTextContent()` (cached per `PDFDocumentProxy`) and `diffTokens.ts` turns the items into words with boxes in page fractions at the page's own rotation (`getViewport({ scale: 1 })` applies `/Rotate`, so drawing only adds `viewer.pagesRotation`). Items that continue a word are joined, line-end hyphens are joined, soft hyphens dropped, text NFKC-normalized, and content order is kept (no reading-order sort, which would interleave columns). Up to `EXACT_LIMIT` (40,000) words in all, the worker diffs the whole token stream with `diff` (jsdiff's `diffArrays`, 4 s timeout) and falls back to page-by-page (300 ms each, then the whole page counts as changed). Longer documents are diffed the way patience diff works (`diffAnchored` in `src/lib/textDiff.ts`, `uniqueRuns` in `src/lib/anchors.ts`): after trimming the common start and end, runs of 8 words that appear exactly once on each side (sampled by hash, so the lookup maps stay small) become anchors, the longest chain of them that stays in order on both sides is kept, and only the gaps between them go through `diffArrays`; a gap over the limit, or one that times out, is paired page by page within the gap. Myers on a million words gives up whenever pages were deleted, and pairing page N with page N then marks everything after the first deleted page as changed. `buildComparison` slides pure insertions/removals to start on a line (`slideToLineStarts`), merges word boxes per line, places a thin marker where text is missing on the other side, notes pages that are wholly added/removed or have no text, and records one anchor per matched line for linked scrolling (`syncLocation`). Highlights are DOM in a `.diff-layer` on each page div, never annotations, so nothing reaches Save. pdf.js's `reset()` removes unknown children on zoom and rotation, so the layer is re-attached on `scalechanging`, `rotationchanging`, and `pagerendered`. Linked scrolling remembers the `scrollTop` it set on the follower and ignores that one echo. Recomputes when either tab's `source` changes (page edits, outside reloads, Swap); markup and form typing don't change the text. Each change keeps an 80-character `before`/`after` snippet for the sidebar plus the full `beforeText`/`afterText` and word counts per side. The Changes tab renders at most `CHANGE_WINDOW` (400) rows around the change in view or the current change (`changeWindow`), with Show earlier and Show later buttons, because a comparison of two unrelated long documents has tens of thousands of changes. The Document Map draws change and find marks only for map pages it keeps rendered, merged per 2 px row (`mergeMarks` in `src/lib/diffRects.ts`). The tab can show all changes or only added, removed, or changed ones, and both the tab and the compare bar count each kind and the words added and removed (`summarizeChanges`, `filteredChanges`, `describeWords` in `src/lib/changeSummary.ts`, which the report uses too). Export Comparison Report (`exportComparison`) lays out a PDF from those in `src/lib/comparisonReport.ts` with `@cantoo/pdf-lib` and its standard Helvetica (WinAnsi only: other characters are NFKD-stripped of accents or drawn as `?`, so no font is fetched or bundled), then saves it through `pick_save_path` + `write_pdf`.
- **Document Map.** `DocumentMap` is a flex sibling of `.viewer-area` in each `DocumentTab` (a pane, not an overlay), on by default and toggled with ⌥⌘B (`clumsy.documentMap`). Its layout comes from the viewer's own page divs (`getBoundingClientRect`, re-measured by a `ResizeObserver` on `.pdfViewer`), normalized by the widest page so zoom doesn't change the map. `layoutMap` in `src/lib/documentMap.ts` fits every page into the pane's height, down to `MIN_PAGE_WIDTH`, then lets the map overflow. The pane's width follows the scaled pages (`layout.width`, at most `MAP_MAX_WIDTH`), so it narrows for long documents; the viewer's fit-width re-fit this causes doesn't feed back, because the layout only depends on the pages' proportions. Viewer and map positions are converted piecewise-linearly between page and gap stops (`toMap`), since the viewer's gaps are fixed pixels at any zoom. When the map overflows, the slider moves linearly with the viewer's scroll ratio and the map content is offset from that, like VS Code; a linear content offset instead makes the slider stall inside pages and jump at gaps. Dragging inverts this with a binary search (`scrollForSlider`). Pages render at the pane's full width, one at a time per document, nearest the viewer's current page first (`createRenderQueue` in `src/lib/renderQueue.ts`, which re-reads the focus before each task, so after a jump the map fills in outward from where you landed), while they're within `KEEP_RENDERED` pages of the map's visible range; outside it their canvases are zeroed so a long document doesn't hold every page it has shown. Thumbnails do the same with an `IntersectionObserver` margin. Both copy the viewer's own canvas when it already has the page at the same view rotation (`publishPageCanvas`/`copyRenderedPage` in `src/lib/pageCanvases.ts`, skipped on pages with form widgets, which the viewer draws as HTML). Thumbnails publish their canvases too, marked `annotated` when they drew the page themselves (so the map can copy them even on pages with annotations), and announce in-flight renders with `trackPageRender`; `copyRenderedPage` waits for one before looking, so the map doesn't decode a scan the thumbnail is already decoding. When they render a page themselves they call `page.cleanup()` afterwards: a `PDFPageProxy` keeps its decoded images in `objs` until then (about 34 MB per scanned page), and only the viewer's own page views clean up when pdf.js evicts them. Both wait while the viewer is scrolling (`useScrolling`) or the tab is hidden (`paused`), like pdf.js's own app renders thumbnails only when the viewer is idle; a `drawn` ref keeps an unpause from redrawing what's already there. Rotation re-renders them. Find marks come from pdf.js's `pageMatches`, which index into the concatenated `item.str`s of `getTextContent({ disableNormalization: true })` with no characters for line ends (that's how pdf.js's own highlighter reads them; `rangeRects` in `diffTokens.ts`), and only show while the find controller's `highlightMatches` is on: pdf.js re-sends the full match count after the find bar closes.
- **Markdown tabs.** `.md`/`.markdown` files open as their own tab kind (`kind: "markdown"`, `MarkdownDocTab` in `src/lib/tabs.ts`), not as a flavor of `"document"`: `kind === "document"` still means "has a pdf.js viewer", so page edits, comparison, image export, and the PDF handle map leave Markdown alone. `isFileTab` covers both where a path or name is all that matters (title, quit, Save All, Reveal in Finder, recent files, dedupe by path). `useWorkspace` keeps separate `markdownHandles` and `markdownSnapshots`; `openSource` takes either source (`isMarkdownSource`). Reading goes through `readDocumentFromPath`, which picks by extension. Text is strict UTF-8 (`decodeText` refuses anything else rather than corrupt it on save) with the BOM and CRLF/LF remembered in `TextFormat` and written back by `encodeText`; Rust `read_markdown`/`write_markdown` are gated by `is_markdown` and use the same atomic write and changed-on-disk stamp as PDFs. The rendered view is markdown-it (`src/lib/markdown.ts`: GFM tables, linkify, task lists, footnotes, front matter as a YAML block, highlight.js common languages without auto-detect) sanitized by DOMPurify (`markdownDom.ts`: no `<style>`, forms, frames, or `target`) and set as `innerHTML` by hand, so find marks and resolved images can be added without React touching them. A core rule stamps every block token with `data-line`/`data-line-end` from its source map and gives headings GitHub-style unique ids. Local images move to `data-local-src` during sanitizing and load through `read_linked_image` as blob URLs (cached per tab, revoked on unmount); `read_linked_image` and `open_linked_file` only resolve relative to an open Markdown file, only return images or `.md`/`.pdf` files, and only reach files inside the link root (`link_root` in `files.rs`): the nearest folder above the Markdown file that holds a `.git`, otherwise the file's own folder. The target is canonicalized before the check, so absolute paths, `..`, and symlinks can't leave it; without that, a page could read any image, PDF, or Markdown file on disk by naming its absolute path. `open_linked_file` puts its result in `ReadOnlyPaths`, a read-only allowlist: reads and stamps accept it, writes answer `not-writable` and Save falls back to Save As, and it never reaches recent files, so a page that calls the command directly can't overwrite a file the user never picked. Remote `https:` images load (`img-src https:` in the CSP). Every link click is handled: `#id` scrolls, http(s)/mailto go to the browser, `.md`/`.pdf` paths open in a tab, anything else is dropped. The sanitizer also removes `<map>`/`<area>`, popovers and their invokers (a popover sits in the top layer, over the whole window), and `href`/`xlink:href` from everything but HTML `<a>`: WebKit makes any MathML element with an `href` a link that navigates the window, and the click handler only intercepts `<a>`. `SANITIZE_NAMED_PROPS` prefixes every `id` and `name` with `user-content-` (like GitHub), so a document can't clobber `window` globals (pdf.js reads `globalThis.FontInspector`, `Stats`, `pdfjsWorker`) or collide with the app's own element ids; heading and `#anchor` lookups go through `anchorIds`. `.markdown-body` has `contain: layout`, so `position: fixed` in a `style` attribute is held inside the document instead of covering the toolbar. The `navigation-guard` plugin (`src-tauri/src/navigation.rs`, `is_app_url`) allows only the app's own origin (`tauri://localhost`, `http(s)://tauri.localhost`, `about:blank`, and the dev server's `http://localhost:1420` in debug builds only; no other localhost port or scheme), and in release builds refuses every navigation after a window's first load: WebKit's default context menu offers Open Link, Back, and Reload, any of which would replace the window and its unsaved tabs. Dev builds keep allowing reloads and Vite's `localhost:1420`. WebKit hands `tel:` link activations to macOS (Continuity "Click to Call") even though the guard refuses the navigation, so the PDF viewer swallows every non-`#` link click, middle-click, and (for anything but http(s)/mailto) context menu itself, and the sanitizer drops `<a>` hrefs with any other scheme (`opensElsewhere`); `openExternal` also refuses anything but http(s)/mailto. ⇧⌘V (`toggleMarkdownSource`, VS Code's Open Preview key) switches to a CodeMirror 6 editor (`markdownEditor.ts`), dynamically imported the first time so rendered-only use doesn't load it, then kept mounted and hidden like inactive tabs so its undo history survives. The editor's host comes before the rendered view in the DOM on purpose: while an editable has focus, WebKit recomputes its editor state on every rendering update, and `Editor::stringForCandidateRequest` walks backward from the caret to the nearest visible character (`isStartOfDocument` → `Position::previous`). With the caret at the top of the file and the hidden rendered article right before it, that walk crossed the whole article every frame and pinned a CPU for as long as the editor kept measuring a 2 MB file. A hidden earlier tab can still sit before it when the sidebar is closed. Position is always a fractional source line: in the rendered view `lineAtOffset`/`offsetForLine` (`markdownScroll.ts`) interpolate inside the innermost `[data-line]` block at the top of the viewport (and between blocks across gaps); in the editor `lineBlockAtHeight`/`lineBlockAt` do the same. Anchoring the top line rather than the middle keeps images and font changes from drifting it. After a programmatic scroll the line is held and re-applied by a `ResizeObserver` while images load, until the user scrolls. That same line is the `MarkdownViewState` (`mode`, `line`, `zoom`) used by outside-change reloads, Reopen Closed Tab, Split Right, and moving a tab between windows (`TabTransfer.format: "markdown"`, UTF-8 bytes through the same stash). Edits re-render the preview only when switching back. Find reuses `compileFindPattern`/`findPatternMatches` over NFD text mapped back to the original (`textFind.ts`), wrapping `<mark>`s in the rendered DOM (`domFind.ts`, rebuilt per query) or CodeMirror decorations in source. Typing waits 250 ms (`TYPING_DELAY` in `useMarkdownFind`, like pdf.js) before searching; option toggles search at once, and Find Next/Previous runs a waiting search first. `highlightMatches` finds each match's text nodes by binary search (`lastPieceBefore`) and wraps every match with one reused `Range`: WebKit updates every live `Range` on each DOM change, so a new one per match made wrapping quadratic. Commands that also make sense for Markdown carry `markdown: true` (save, find, sidebar, outline, zoom, first/last page as top/bottom); `needsMarkdown` commands only work there; `documentAvailable` applies both to the menu, the palette, and `runCommand`, and `useMarkdownCommands` handles them before the PDF routers. Native Undo/Redo reach CodeMirror only through `editingCommand`, since the menu accelerator swallows ⌘Z before the editor's keymap sees it; in source mode they go to the editor's history unless another text field (the find bar) has focus, so the Command Palette's Undo works too. The minimap (`MarkdownMap`, shown with the same `clumsy.documentMap` toggle and ⌥⌘B as the PDF Document Map) is a canvas the size of the map pane, painted from shapes measured on the real `<article>` (`collectShapes` in `src/lib/markdownMapShapes.ts`): one bar per text line box (`Range.getClientRects`, colored by the text's computed color and cached per tag, class, and muted context), backgrounds and borders of code, quotes, rules, headings, and table cells, the loaded `<img>`s themselves, and find marks. Only the visible slice is painted, so scrolling stays cheap, and the article height (over a million pixels for a 2 MB file) never becomes a canvas. It used to be a clone of the whole article, which doubled the DOM (86k extra nodes for the 2 MB fixture) and re-laid it out on every find query and image load. Shapes are re-measured (debounced) when the article resizes or its content changes; changes that only add, remove, or recolor find marks (`onlyFindMarks`) re-measure just the marks. The system color scheme changing re-measures everything, since the colors are read from computed styles. Its slider reuses `sliderFor`/`scrollForSlider` with a one-block layout (`documentLayout` in `src/lib/markdownMap.ts`). In source mode there's no rendered scroll position, so the editor's visible line range is mapped onto the rendered layout with `offsetForLine` (`sourceViewport`) and map clicks and drags scroll the editor to `lineAtOffset` of the target, the same line mapping the ⇧⌘V toggle uses. Live reload uses the same polling as PDFs; a Markdown tab reloads when its text matches the last saved text and it has no carried changes.
- **Pages as images.** Export Pages as Images (File menu) and Export Selected Pages as Images (Pages menu, thumbnail context menu) are the same command: the sheet offers all pages, the current page, the selection (`explicitPages`, same `followCurrentPage` rule as other page commands; shown only when there is one and picked by default), or a typed range like "1-3, 5, 8-" (`parsePageRange` in `src/lib/pageRanges.ts`; an empty or invalid range disables Export). Resolution is 72, 150, or 300 dpi, with the current page's pixel size shown (`exportPixelSize`). The last format, resolution, and JPEG quality are kept in `clumsy.exportImages`; the page choice isn't. Pages render from the tab's loaded pdf.js document unless the tab has unsaved Clumsy-owned changes (`clumsy-markup:` or `clumsy-note:` storage keys, `hasOwnedChanges`), which pdf.js can't draw; then they render from a temporary document loaded from `viewer.save(true)`'s bytes (with the tab's password), destroyed afterwards. pdf.js's print path (`intent: "print"`, `AnnotationMode.ENABLE_STORAGE`, `printAnnotationStorage: annotationStorage.print`) draws unsaved markup and typed form values the way they'd print, after `commitEdits()` and `settled(tabId)`. The storage snapshot is taken once, so edits made while an export runs aren't in it. Each page renders into its own detached canvas, one at a time, then the canvas is zeroed and `page.cleanup()` frees that page's operator lists and images (this also drops the on-screen page's cached operator list; pdf.js refetches it on the next render). Output honors the page's saved `/Rotate` (`getViewport` applies it) but not the view-only rotation (⌘R), which isn't part of the document. Scale is dpi/72, capped at 2^25 pixels and 16384 px per side (`renderScale`) so huge pages don't fail to allocate. One page goes through a save dialog as "<doc> - page 3.png"; several go into a picked folder as "<doc> - page 01.png", zero-padded to the document's page count. If any of those names already exist, Clumsy asks once ("Replace" or "Cancel") before writing anything. Rust asks (`confirm_replace`, a native alert), not the webview, and remembers the files the user agreed to replace; `write_image` replaces only those, once each, so a page can't overwrite other images in a picked folder by claiming consent. Everything else Rust opens with `create_new`, so nothing is ever replaced silently, even if a file appears mid-export. Cancelling stops after the current page and keeps the files already written. When at least one file was written (including a cancelled export), a native alert offers Show in Finder, which reveals the first file; `write_image` returns the path it wrote for this.
- **Printing.** Print (⌘P, File menu) and Print Selected Pages (Pages menu, thumbnail context menu) go through PDFKit, not the webview: WKWebView's own print prints the whole window and only the pages pdf.js has rendered, wry doesn't wire `window.print()` on macOS, and pdf.js's print service rasterizes every page. `usePrint` waits for `settled(tabId)`, works out the pages only then (a page edit still running when the command fired would otherwise shift them), takes `viewer.save(true)` (the bytes Save would write, with unsaved markup, typed form values, and sticky notes), and hands them to Rust's `print_pdf` (`src-tauri/src/print.rs`) as a raw body with the tab name in `x-name`. Rust hops to the main thread, opens the bytes as a `PDFDocument` (`initWithData:`, no temp file), and prints them through its own view, `ClumsyPrintView` (`define_class!` in `print.rs`, an `NSView` with `knowsPageRange:`, `rectForPage:`, and `drawRect:` that draws each `PDFPage` with `drawWithBox:toContext:`, which applies the page's `/Rotate`), not PDFKit's `printOperationForPrintInfo:scalingMode:autoRotate:`. PDFKit's print view picks its scaling once, from the paper when the operation is made, and has no way to change it, so with a 4×6 label printer as the default every Letter page stayed shrunk after switching to a Letter printer. The custom view reads the print info's paper and printable area every time AppKit repaginates (each printer, paper, or orientation change in the panel), `drawRect:` draws only the pages its dirty rect covers (`pages_in`), and `place` (`src-tauri/src/print_layout.rs`, pure and tested) decides each page: actual size, centered on the sheet, when it fits either way round (turned if it only fits sideways); otherwise scaled to the printable area, turned when that shrinks it less. Scaling only pages that don't fit matters because the printable area isn't the sheet (the Brother's is 576×734 of 612×792): always fitting it shrank a Letter page about 7% on every Save as PDF and print of the result. The print info is a copy of the shared one with zero margins (the default inch did the same), and the panel adds Paper Size, Orientation, and the preview (`NSPrintPanelOptions`). The paper is the panel's: macOS keeps the last paper when you switch printers if the new one accepts it (a label printer takes custom sizes, so Letter stays), and Paper Size is how to change it. Pinning the paper to the document's page size was tried and left every printer previewing Letter. The sheet goes on the calling window, with the job titled after the document (the default name for Save as PDF). It answers `shown`, `unreadable` (PDFKit couldn't open it; the app shows an error), or `busy` (a sheet is already up on that window; nothing happens). `save(true)` matters: pdf.js's `saveDocument()` calls `annotationStorage.resetModified()`, which would mark an edited tab as saved, so `saveKeepingModified` (`src/lib/print.ts`) shadows that method on the storage for the one save. Because that shadow would also swallow a real Save's reset, every `viewer.save()` runs one at a time (`oneAtATime`), so Save, page edits, and tab moves wait for a print's save to finish. What prints is what Save would write: page content, the saved `/Rotate`, markup with the Print flag, form values. Find, comparison, selection, and Document Map highlights, form field shading, and the view-only rotation (⌘R) don't. Print and copy permissions are ignored: a file pdf.js opened (with its user password, or with no password when it only has an owner password) is decrypted in the page-edit worker (`decrypt` job, `decryptPdf` in `pageEdits.ts`, with the password `loadPdf` recorded per document in `passwordOf`, or `""`) before PDFKit sees it, so no password crosses IPC and PDFKit's blank pages on print-restricted files never come up. Encryption is detected from `getMetadata()`'s `EncryptFilterName`; plain files skip the worker. Print Selected Pages runs the existing `extract` job on the selection (or the current page, like other page commands), decrypting in the same pass; a selection covering every page prints the whole file. pdf-lib's decryption writes decrypted literal strings back unescaped, so a decrypted `(`, `)`, or `\` (or the garbled `/ID` of an RC4 file pdf.js saved) broke the output; `installDecryptedStrings` (`src/lib/pdfDecrypt.ts`) makes the parser return decrypted strings as hex strings with the exact bytes. Printing never touches the tab's edit state, undo stacks, or the file on disk. Only macOS can print (`canPrint` in `platform.ts`); elsewhere `needsPrinting` commands are left out of the menu (`visibleSlots`, which also drops the separators they leave), the palette, the Shortcuts sheet, and the thumbnail menu. **Image fallback.** `printWithFallback` (`src/lib/print.ts`) prints the pages as images when pdf-lib can't decrypt or extract the saved bytes or PDFKit answers `unreadable` (a header CoreGraphics rejects, damage pdf.js repaired on open). `pdfFromRenderedPages` (`src/lib/rasterPrint.ts`, loaded on first use with pdf-lib) renders each page from the tab's own pdf.js document with `renderPageImage` and `annotationStorage.print`, like Export Pages as Images, as a JPEG (quality 0.85) at 300 dpi up to 50 pages, 200 up to 200, 150 up to 500, then 100 (`rasterDpi`): every JPEG stays in memory until pdf-lib writes the file, which then exists twice more (the saved buffer and its IPC copy), so the tiers keep a long scan to a few hundred megabytes, and draws each one on a page of the page's own size (with its saved `/Rotate`), so the panel scales it like the original. `PrintProgressDialog` shows progress with Cancel and says the file prints as images. A failed save (`viewer.save`) is a real error, not a reason to rasterize, so it's shown; a save that comes back empty or from a document the tab no longer shows (it reloaded or closed meanwhile) just ends the print. Native menu commands still run while the progress sheet is up, so each page checks the tab still shows the same document and stops with an error if a page edit or reload replaced it. When the tab has unsaved Clumsy markup or sticky notes (`hasOwnedChanges`), the images render from a fresh `viewer.save(true)` loaded into its own pdf.js document (destroyed afterwards), so they're in the images; otherwise from the tab's storage. **Markdown.** Print on a Markdown tab (`markdown: true`; Print Selected Pages stays PDF-only) copies the rendered article (`printCopy`, find marks removed) or, in source view, renders the editor's current text into a fresh `<article>` (`printableArticle`, so unsaved edits print), with local images loaded and every image switched to `loading="eager"` (the sanitizer makes them all lazy, and lazy images in the clipped root never load), puts it in a `.markdown-print` root at the end of `<body>`, and calls Rust's `print_webview`, which runs the WKWebView's own `printOperationWithPrintInfo:` as a sheet. WebKit lays the live document out in print media for as long as the panel is open, so `Markdown.css` hides the rest of `<body>` with `visibility: hidden` and pins it, fixed, at the window's own pixel size (`--app-width`/`--app-height`, set by `printArticle`): `display: none` or letting it reflow at the paper's width made every hidden PDF viewer re-fit its zoom and come back on a different page. The root gets light colors (the highlight.js dark colors are `screen`-only), wrapped code, and tables at full width with `table-layout: fixed` so wide ones wrap instead of running off the paper. `.markdown-body` keeps `contain: layout` in print too, so a `position: fixed` element in the document stays inside it instead of repeating on every page. On screen the root sits behind the app (`position: fixed; z-index: -1`) rather than `display: none`: WebKit never decodes images in a `display: none` subtree, so they printed blank and `decode()` waited out its 5 s cap. The operation's view gets the web view's bounds (a zero frame prints blank pages), margins are half an inch, and the job is titled without `.md`, so Save as PDF names the file `Notes.pdf`. A small delegate (`ClumsyPrintDelegate`) sends on a channel when the sheet ends, so the command resolves only then and the root is removed after the job, not while the panel is still drawing previews from it. The wait also polls once a second and gives up if the window is gone, so a window closed under the sheet doesn't leave the command pending.
- **PDFs from images.** New PDF from Images (File menu), dropping images on the window, and Insert Pages from File (which now picks PDFs and images, several at once) all go through `src/lib/imagePdf.ts`. Dropping or picking a mix keeps the order: consecutive images become one PDF (`groupRuns`), PDFs stay as they are, and the pieces are combined. Away from the thumbnails, dropped PDFs open as before and all the dropped images become one new unsaved tab (`carriedChanges`), named after the first image ("IMG_0001 and 3 more.pdf"). Inserting goes through `usePageEdits` (`insertFiles` → `performEdit`), so undo, redo, and the generation rules are unchanged. One page per image; the page is the image at 72 pt per inch (one pixel to a point), shrunk to fit Letter in the image's own orientation and never enlarged (`imagePageSize`). JPEGs are embedded byte for byte and never recompressed: their EXIF orientation is read (`jpegOrientation`) and applied with the image's `cm` matrix (`orientationMatrix`), which handles flips too. PNGs are embedded as-is (pdf-lib re-deflates them losslessly). Anything else, or a PNG/JPEG pdf-lib can't parse, is decoded by the webview through an `<img>` and a canvas (which applies HEIC/TIFF orientation) and embedded as PNG if any pixel is transparent, otherwise JPEG at 0.92. Big photos aren't downsampled.
- **Page edit timing.** `usePageEdits` keeps per-tab state: a queue (edits run one at a time), the `pending` version (shown but not yet loaded by pdf.js; the next edit starts from it), a `generation` counter, and up to 20 earlier versions (`trimHistory`). The pdf-lib work (`applyPageEdit`, `extractPages`, `combinePdfs`, and counting an inserted file's pages) runs in a module worker, one per job (`runInWorker` in `src/lib/pageEditWorker.ts`, `answerPageEditJob` in `pageEdits.ts`), so a large file doesn't freeze the window and pdf-lib isn't loaded on the main thread for it. Bytes are transferred, not copied: an edit's input comes back as `original` and is what goes on the undo stack, so nothing may read `before.bytes` after it's sent. Errors cross as `{ message, pageEdit }` (`src/lib/pageEditMessages.ts`) and come back as `PageEditError` or a plain `Error`. Decoding images for inserts needs the webview's canvas, so `imagePdf.ts`/`imageImport.ts` stay on the main thread; only combining the pieces goes to the worker. Every tab's undo and redo versions share one 256 MB budget per window (`shareBudget`, run after every edit, undo, and redo): over it, the tab holding the most loses its oldest undo version, then its farthest redo, and each tab always keeps its newest undo version, which `documentFailed` needs. Commands capture the generation when issued and are dropped if another edit landed first, because their page indices refer to the old version. History belongs to one `source` object: if anything else replaces the tab's source (an outside change reloading the tab), the history is cleared, and an edit whose baseline changed while it was computing is cancelled. Save and moving a tab to another window first `await settled(tabId)`. Save only clears `carriedChanges` if the source it saved is still the tab's source. If pdf.js can't open an edited version, `documentFailed` restores the previous one instead of closing the tab. Undo and Redo are routed by `routeStep`: Undo goes to pdf.js while pdf.js has something to undo (`viewer.editHistory()`, from pdf.js's `editingstateschanged` event, so it survives Save), otherwise to page history, except after the user typed into a form field since this version loaded (`changed`, set by `input`/`change` events inside the annotation layer; typing isn't on pdf.js's undo stack, and page undo would take the typed values with it). Don't use `annotationStorage` modification for this: pdf.js writes to it while rendering radio buttons. Redo goes to pdf.js while pdf.js has something to redo; if markup or typing sits on top of the current version, page redo is cleared instead, because those versions predate it. While an edit is queued or a version is loading, Undo and Redo are queued behind it instead of going to pdf.js. `documentLoaded`/`documentFailed` get the `source` that finished loading and ignore stale ones, so a quick Undo can't clear the wait for a newer version. Selection lives in `DocumentTab` and only counts while it includes the current page (`followCurrentPage`), so scrolling away quietly drops it; commands act on the selection or else the current page. Dragging to the same spot is a no-op (`changesDocument`). Thumbnail drag-to-reorder is pointer based like tab dragging. Dropping PDFs or images on a visible sidebar inserts them at the drop line (`src/lib/dropTarget.ts`, marked with `data-drop-*` attributes React doesn't manage); dropping anywhere else opens them as before. The thumbnail context menu is a native popup (`showContextMenu`).
- **File access.** The webview can only read or write paths Rust handed out: files picked in Rust's dialogs (`pick_pdf`, `pick_document` for Open, which takes PDFs and Markdown, `pick_pdfs`, `pick_save_path`, `pick_markdown_save_path`, `pick_image_save_path`), documents dropped on a window, opened from Finder or the command line, or in recent files. `files.rs` keeps that allowlist (canonical paths) and `read_pdf` / `read_markdown` / `read_image` / `write_pdf` / `write_markdown` / `record_recent_file` check it, so a compromised page can't read arbitrary files. Each command also checks the extension (`is_pdf`, `is_markdown`, `is_image`), so a Markdown path never reaches `write_pdf` or the reverse. Files that are only read go in `ReadOnlyPaths` instead (reads and stamps only, never writes or recent files): files reached from a Markdown link, images and PDFs picked to place or insert (`pick_image`, `pick_images`), and dropped images. Otherwise picking photos for New PDF from Images would let `write_image` overwrite them. Images a Markdown file shows are read through `read_linked_image` without being allowed at all; see Markdown tabs. File drops are ignored while any `<dialog>` is open (`sheetOpen` in `onFileDrop`), since Tauri delivers them to the window, not to the element under the pointer; sheets that need a file use a picker. Folders picked with `pick_folder` go in a separate folder allowlist; `write_image` writes only `.png`/`.jpg`/`.jpeg` files, either to an allowed path or to a plain file name (no separators, `.`, or `..`) directly inside an allowed folder, and `confirm_replace` only answers for allowed folders and image names. `write_pdf` never writes images and `write_image` never writes PDFs. Don't call the dialog plugin's `open`/`save` from JS for files; add a Rust command that allows the result. File IPC commands are `async` so large reads and writes don't block the main thread (sync commands run on it). The CSP lives in `tauri.conf.json`; `devCsp` is `null`, so `pnpm tauri dev` doesn't enforce it. Check CSP changes with a `pnpm tauri build` app.
- **Passwords.** A document tab can carry `protection: { password, ownerPassword? }` (`DocTab.protection`, `src/lib/protection.ts`): the open password Save writes with. It lives on the tab, not the source, so learning it doesn't replace the source and reload the viewer. Once Clumsy has rewritten a protected document (a page edit, sticky notes, Set Password on an encrypted file), the tab works on plain bytes in memory, and Save and Save As encrypt them on the way to disk: `bytesForDisk` leaves bytes alone when the tab has no protection or they already carry `/Encrypt` (`hasEncryptEntry` reads the trailer of the cross-reference section the last `startxref` points at, walking a classic table's subsections to reach it, since a linearized file's main trailer at the end has no `/Encrypt`; or the cross-reference stream's dictionary; `null` when it can't tell; a markup-only save of an opened protected file is pdf.js's incremental update, still encrypted), and otherwise runs the worker's `encrypt` job (`encryptPdf` in `pageEdits.ts`: `collectGarbage`, `encrypt` with the same user and owner password, AES-256, full rewrite with object streams). Opening a protected file sets `protection` from the password pdf.js accepted (`documentLoaded` in `usePageEdits`). Owner-only files (restrictions, no open password) get none: they open without a prompt and lose their restrictions once Clumsy rewrites them (page edits, sticky notes), but keep them on a save that only adds other markup or form values. pdf.js also accepts a file's owner password at the prompt, and encrypting with it would lock out everyone who only has the user password, so after a typed password opens a file, `DocumentTab` asks the worker in the background (`role` job, `passwordRole` in `pdfDecrypt.ts`, from `doc.getData()`) whether it was the owner password; if so the tab's protection gets `ownerPassword: true` (`ownerPasswordUsed`), and the first Save that would write fresh encryption asks first (`confirmOwnerPassword`). `passwordRole` reaches pdf-lib's unexported key factory through the parser that receives it, subclasses it with the owner path disabled (`decodeUserPassword` for RC4/AES-128, a zeroed `O` hash for AES-256), and constructs it again with the same dictionary, file ID, and password. Set Password… (`PasswordSetDialog`, an in-window sheet opened through `DocumentHandle.editPassword`, titled Change Password on a protected tab, never asking for the current password) and Remove Password (`needsProtection`, enabled only on a protected tab, like `needsForm`) are page edits (`{ kind: "protect", password }`). The worker always decides: it loads `viewer.save()`'s bytes with the version's password and returns them decrypted, or `unchanged` when pdf-lib didn't decrypt anything; an unchanged result only changes the tab's protection (`protect` in `usePageEdits`, marked edited, with an undo version) and doesn't reload the viewer. Every `Version` and `currentVersion` carries `protection`, and `show` writes it onto the tab with the new source, so undo and redo restore it with the bytes. `DocumentTab` answers pdf.js's password request with the tab's protection, then the last protection that opened this tab (`lastProtection`, which also survives an outside-change reload clearing the tab's protection, since that reload reads the file from disk), before showing the prompt (`passwordAnswers` in `src/lib/passwordAnswers.ts`); so undo, a failed edit restoring the previous version, and reloads never ask for a password Clumsy already has. Moving a tab stashes its password as a separate transfer blob (`passwordId`, taken once), so it never appears in a window URL; a move that fails takes both blobs back (`discardTransfer`), and a window that never loads leaves them until the stash's five-minute expiry. Extracted pages keep their document's protection. The tab strip shows a locked file icon and "Password protected" in the tooltip (`tabItemFor` in `tabs.ts`). Three pdf-lib gaps are worked around in `src/lib/pdfDecrypt.ts`. Its decrypting parse can't read a cross-reference stream's trailer, so `/Info` (title, author) was lost for nearly every modern encrypted file: `loadDecrypting` captures the trailer from pdf-lib's own first, non-decrypting parse (by wrapping `PDFParser.forBytesWithOptions`) and restores the `/Info` reference, with no extra parse. Its writer encrypts streams but never strings, and keeps the catalog, page tree, pages, signature dictionaries, objects with a nonzero generation, and every stream out of object streams, so `encryptUncompressedStrings` encrypts the strings in exactly those objects (stream dictionaries included, a signature's `/Contents` excepted) and leaves the rest to the encrypted object streams; it mirrors `PDFStreamWriter`'s `shouldNotCompress`, so check that list when upgrading pdf-lib. For the same reason `encryptPdf` must keep `useObjectStreams: true`: with a classic cross-reference table pdf-lib leaves every string in plaintext, and readers decrypt them into garbage. Also don't drop `collectGarbage` from a decrypting save: pdf-lib keeps the old cross-reference stream as an ordinary object, which still says `/Encrypt`, and the next load reads the file as encrypted.
- **Quitting.** Quit is a custom command (⌘Q), not the predefined item, because the predefined one terminates without any chance to ask. It reports this window's documents (finishing in-progress edits first) and calls `request_quit`, which exits right away or shows one native "Discard and Quit" alert listing every unsaved document across windows. Quitting from the Dock or logging out still skips the prompt: tao doesn't implement `applicationShouldTerminate`.
- **Dark pages.** The default ("Keep images") applies `invert(0.92) hue-rotate(180deg)` to `.canvasWrapper` and the editor layer, then draws each image's original pixels into an unfiltered overlay canvas (`.image-restore`). The overlay is only drawn while dark pages and "Keep images" are both on (`setImageRestore`); otherwise it's removed, since it's a full-size copy of every page with an image. Thumbnails and the Document Map do the same at their size: only their page canvas is inverted, and an `.image-restore` canvas beside it gets the image pixels (`usePreviewImages`, `restorePreviewImages`), drawn only while both settings are on. When they render a page before the viewer has, they ask pdf.js to record its images (`previewRender`, stretched with `fillTransform` so the canvas-relative coordinates pdf.js keeps on the page are exact page fractions the viewer can reuse). Image rectangles come from pdf.js's image tracker (`imagesRightClickMinSize: 0`) and are rotated by `src/lib/imageRegions.ts`. pdf.js's own `pageColors` high-contrast mode recolors images too, so it isn't used. `enableDetailCanvas` stays off: pdf.js draws the detail canvas inside `.canvasWrapper`, under the `.image-restore` overlay, and `restoreImages` copies image pixels from the base canvas (it skips detail renders), so at high zoom images would show at the base canvas's lower resolution on top of the sharp detail render. Turning it on means restoring images from the detail canvas too, at its offset.
- **Fit width / fit page on resize.** `usePdfViewer` re-applies preset zooms when the viewer's *border-box* size changes. Don't observe the content box: with always-visible scrollbars the scrollbar appearing narrows the content box, the page re-fits smaller, the scrollbar disappears, and the page loops forever (it shakes and pins a CPU). `.viewer-container` also uses `scrollbar-gutter: stable`.
- **Recent files.** Rust owns the list (`~/Library/Application Support/com.ry4nolson.clumsy/recent-files.json`, max 20, menu shows 10) so the native menu works before the webview loads. The frontend records a path after a successful load or a Save As, and listens for `recent-files-changed`.
- **Default PDF and Markdown app.** `default_app.rs` calls `LSCopyDefaultRoleHandlerForContentType` / `LSSetDefaultRoleHandlerForContentType` for `com.adobe.pdf` (what `duti` uses), or `net.daringfireball.markdown` for Make Clumsy the Default Markdown App (macOS declares that UTI itself; JS passes `"pdf"` or `"markdown"`, never a raw UTI). Only offered when running from an installed `.app`; dev builds aren't registered bundles. Only PDFs get the launch prompt. Every `pnpm tauri build` bundle (worktrees, scratch builds, mounted release DMGs) shares the bundle id, and Finder registers each one it sees, so on a dev machine double-clicking a PDF can open a stale build instead of `/Applications/Clumsy.app`. List the registered copies with `lsregister -dump | grep -B2 -A25 com.ry4nolson.clumsy`, unregister strays with `lsregister -u <path>/Clumsy.app`, eject old DMGs, and re-register the installed one with `lsregister -f /Applications/Clumsy.app` (`lsregister` lives in `/System/Library/Frameworks/CoreServices.framework/Frameworks/LaunchServices.framework/Support/`).
- **Scroll and spread modes.** `viewer.scrollMode`/`spreadMode` reset on every `setDocument`, so they're applied in `pagesinit` before the zoom and location, from the tab's `ViewState` if it has one, otherwise the last choice (`clumsy.scrollMode`/`clumsy.spreadMode`, written only when the user picks a mode). They live in `ViewState`, so they survive tab moves, Reopen Closed Tab, outside-change reloads, and page edits. The Document Map lays pages out in rows (`pageRows`: pages whose boxes overlap vertically share a row), which covers spreads and wrapped scrolling. `MIN_PAGE_WIDTH` applies to each page, not the row. In wrapped scrolling the pane stays at `MAP_MAX_WIDTH` and centers its content: how many pages fit in a row depends on the viewer's width, so a pane that followed the layout's width would loop with the viewer (the same shake as fit width). Horizontal and page scrolling hide it, disable its menu item, hide it from the Command Palette, and ignore ⌥⌘B (`documentMapAvailable`), because the map follows vertical scroll. Next/Previous Page and the Space tap use pdf.js's `nextPage`/`previousPage`, which step by spread. `scrollLocation` reports the first page of a row, so linked scrolling follows the left page of a spread. Linked scrolling in a comparison is skipped while either side scrolls horizontally or by page (`CompareView.linkable`), and Next/Previous Change first sets the current page in those modes so `revealRect` has a laid-out page to scroll to.
- **Back and forward.** pdf.js's `PDFHistory` drives `window.history` and assumes one document per page, so each viewer keeps its own stack (`src/lib/navHistory.ts`, at most 50 stops) and plugs an adapter into `linkService.setHistory`: `pushCurrentPosition` records the current `updateviewarea` location before link and outline jumps, and the `GoBack`/`GoForward` named actions step it. Go to Page, first/last page, the palette's `:page`, the first find of a search and every Find Next/Previous, and comparison change jumps record explicitly (`recordStop`, `goToPage(page, true)`); ordinary scrolling and Next/Previous Page don't. Stepping pushes the current spot onto the other stack and scrolls with an XYZ destination, so it survives zoom changes. The stack is part of `ViewState`; page edits remap its pages with `pageAfterEdit` (`remapStops`). A jump updates the stored location right away, so two quick Back presses don't both start from the same spot. Mouse buttons 3 and 4 also step it; trackpad swipes don't (WKWebView's swipe gesture is its own back/forward navigation).
- **Opening a document's own view.** On a fresh open (no `ViewState`, and the path isn't in recent files yet, so only the first time a file is opened) `DocumentTab` reads `getOpenAction` (a `Map` in pdf.js 6), `getPageMode`, and `getPageLayout`. `documentView` in `src/lib/viewModes.ts` maps them: `UseOutlines`/`UseThumbs` open the sidebar on Outline/Pages, and `SinglePage`, `OneColumn`, `TwoColumnLeft/Right`, `TwoPageLeft/Right` become scroll and spread modes. The open action's destination is scrolled to without recording a history stop. Restores always keep the saved view.
- **Page labels.** `getPageLabels()` is loaded on every document load and handed to `viewer.setPageLabels` once pages exist; labels that are just "1", "2", … are treated as none. The page box shows the label with "(n of N)", and `pageFromInput` takes an exact label, then a case-insensitive one, then a number.
- **Hand tool and Space.** `src/lib/handTool.ts` pans the container from a capture-phase `pointerdown`, so it also works over the editor layers without switching pdf.js's editor mode. Tools > Hand sets the editor mode to none and turns it on; holding Space turns it on until release from any tool (`holdHand`), except in text fields, form fields, free text editors, and buttons (`wantsSpace`). A tap of Space without a drag scrolls a screen (Shift goes back), since the keydown is prevented.
- **Editor managers.** pdfjs-dist ships the editors but not the viewer-app pieces they call for comments, signatures, alt text, and the undo bar (Firefox's `CommentManager`, `SignatureManager`, `AltTextManager`, `EditorUndoBar` live in `web/` and aren't exported). `src/lib/editorManagers.ts` (with the comment manager split out into `commentManager.ts`) implements their interfaces per viewer and passes them to `PDFViewer` (`commentManager`, `signatureManager`, `altTextManager`, `editorUndoBar`); the methods pdf.js calls are exactly the ones in Firefox's `web/*_manager.js` for the pdfjs-dist version, so check those when upgrading. Each one turns a call into a request in a small store (`subscribe`/`getState`, read with `useEditorUi`) that a React sheet answers through `finish*`, which calls back into the editor (`altTextData`, `addSignature`, `comment`) and re-adds the UI manager's edit listeners that the request removed. Having a `commentManager` changes pdf.js: every editor's toolbar gets a Comment button, the floating button over selected text gets Comment, and existing annotations' popups render as comment buttons through `CommentPopup` (`src/lib/commentPopup.ts`, a port of Firefox's, DOM inside the page layers) instead of pdf.js's classic popups. The Comments tool is pdf.js's `POPUP` mode: entering it calls `showSidebar` with every comment, and the Comments sidebar tab only exists while it's on (like Changes). Sidebar clicks use `linkService.goToXY`, then `waitForEditorsRendered` and `selectComment` on the UI manager, which pdf.js hands the comment manager through `setSidebarUiManager` when it builds the UI manager. Grep both `build/pdf.mjs` and `web/pdf_viewer.mjs` for `commentManager?.`, `signatureManager?.`, `altTextManager?.`, and `_editorUndoBar?.` to see every method they call. The undo bar's Undo goes through `usePageEdits.undoIn(tabId)` (the same routing as Edit > Undo, for the bar's own tab even when another pane is focused) rather than calling pdf.js's closure, so the command stack stays in step and it waits behind queued page edits (pdf.js hides the bar on every other command). Signatures use pdf.js's `SignatureEditor`, which turns typed text (an `OffscreenCanvas` in the type field's computed font), drawn curves, or an image's contours into vector outlines; saved ones are `SignatureExtractor.compressSignature` strings in `clumsy.signatures` (at most 5, `src/lib/signatures.ts`), shared by every window through the `storage` event. The old `clumsy.signature` PNG is converted with `SignatureExtractor.process` and only removed once the converted one is written, so a failed conversion keeps it. `loadSignatures` (which pdf.js awaits on entering `SIGNATURE` mode) re-reads the saved list every time, because other tabs in the same window don't get `storage` events. Sign enters `SIGNATURE` mode and, with nothing saved, creates an editor with no data, which makes pdf.js call `getSignature`; saved ones are placed with a `CREATE` param carrying `signatureData`. `HIGHLIGHT_SHOW_ALL` isn't echoed back by pdf.js when we set it, so `setEditorParam` records it locally. Highlight/Comment on Selected Text only run when the selection is in this viewer's text layer, since pdf.js assumes it is, and switch to the Highlight tool first unless Select or Highlight is on: pdf.js creates the new editor with the current mode's editor class, so from Draw it would make a drawing. Comment popups and editor toolbars are counter-inverted on dark pages. pdf.js's own CSS uses a few variables only Firefox's `viewer.css` defines (`--comment-edit-button-icon`, `--main-color`, `--toolbar-icon-bg-color`, `--icon-size`, `--dir-factor`, `--editor-toolbar-min-width`); `Editing.css` sets them on `:root`, or the comment buttons draw as blank squares. pdf.js also hides comment popups, editor toolbars, the highlight color menu, and hidden highlights with a `hidden` class that only that file styles, so `Editing.css` gives `.pdfViewer .hidden` `display: none`. pdf.js gives the Draw and (on high-resolution displays) Text cursors a hotspot of `0 16` on 16×16 images, one pixel outside the image; WebKit draws the default arrow for an out-of-bounds hotspot (older versions used the top-left corner, so ink started above the pencil's tip), so `Editing.css` redefines both on `.pdfViewer` with `0 15`. pdf.js writes a text box's own text as its `/Contents` and then shows that as a comment when the file reopens (a comment button and a popup on hover), even though text boxes can't take comments, so `pdfjs.ts` wraps `AnnotationLayer.prototype.render` and `withoutTextBoxComment` (`src/lib/comments.ts`) drops `contentsObj` and `richText` from FreeText annotations that have no `/Popup` of their own. Alt text is saved as a `Figure` in the structure tree, which pdf.js creates for an untagged file but only updates in a tagged one whose `StructTreeRoot` has `ParentTreeNextKey`; otherwise it drops new alt text silently (some producers omit the key). A UI manager only learns its editor types when the first page's editor layer is built, after that page renders, and pdf.js's `POPUP` mode crashes (and leaves every later mode switch waiting forever) if it starts before then, so `setEditorMode` waits for the first `annotationeditorlayerrendered` of each document before switching to any editing mode, counting only events from the current document's page views that actually built an editor layer. Annotation icons pdf.js still draws (replies to sticky notes, file attachments) come from `imageResourcesPath`, which points at `pdfjs/images/` (the `annotation-*.svg` files are copied there by `vite-plugin-static-copy`, like cmaps and fonts). pdf.js turns a file's existing highlights, notes, drawings, and stamps into editors when any editing mode starts, and doing so marks the document modified, so a file with markup reads as edited after picking a tool; that predates comments. Popups on markup pdf.js can't write back (underlines, strikeouts, shapes from other apps) hide Edit and Delete (`savesComment` in `commentManager.ts`), because pdf.js would drop those changes on Save. pdf.js also has no sticky-note editor and can't write `/Text` annotations, so Clumsy owns them (see Sticky notes).
- **Forms.** pdf.js renders and fills AcroForm fields (`AnnotationMode.ENABLE_FORMS`) and writes their values on save; Clumsy adds navigation, reset, flattening, and marks for paper forms. Each viewer reads `getFieldObjects()` on load (`useViewerForm`, `readFields` in `src/lib/formFields.ts`); the tab's `hasForm` gates the `needsForm` commands in the menu and palette. `tabOrder` sorts fillable, editable, visible fields by page, then row (tops within half a field's height count as one row), then left; Tab and ⇧Tab in a field and Next/Previous Form Field step through it with wrap-around, scrolling to a field's page and waiting for `annotationlayerrendered` when its element doesn't exist yet. Without a focused field they start from the last field used if it's on the current page, otherwise from the current page. Reset Form follows pdf.js's own ResetForm action (`resetEntry`): each field's storage entry is replaced (remove, then set, like sticky notes), rendered elements get pdf.js's own `resetform` event (setting `value` directly isn't enough: a text widget caches its file text as `formattedValue` and puts it back on blur), undo writes the earlier values back into the elements, and the whole reset is one command on pdf.js's undo stack through `editorUi.addCommands`. Undo removes entries that weren't there before, so untouched fields keep their own appearance on save. Flatten Form is a page edit (`{ kind: "flatten" }`, `flattenForm` in `src/lib/pdfForm.ts`), so it starts from `viewer.save()`, is queued and undoable, and marks the tab edited. pdf.js saves values without appearance streams when a form has `NeedAppearances`, and leaves the old, possibly stale ones on fields nobody changed, so with `NeedAppearances` every text and choice field is redrawn with pdf-lib's Helvetica first; without it, only fields missing an appearance are. A field that can't be redrawn (text that isn't WinAnsi) is left as a field rather than flattened with a stale or missing appearance. Each widget's normal appearance (its `/AS` state for checkboxes and radios, or the field's `/V` when `/AS` is missing) is drawn with the transform from PDF's Algorithm 8.1 (`appearanceTransform`: the appearance's `/BBox` through its `/Matrix`, fitted to `/Rect`), which pdf-lib's own `flatten` skips. Hidden and NoView widgets, signature fields, and push buttons without an appearance are dropped without drawing. Flattened widgets leave `/Annots`, their fields leave `/Fields` (`pruneFields`), their structure elements go (`pruneStructTree`), other references are nulled (`detach`), XFA is dropped, and `/AcroForm` is removed once no fields remain. View > Highlight Form Fields (`clumsy.fieldHighlights`, on by default) only toggles pdf.js's field shading and required outline with a `hide-field-highlights` class on the app.
- **Fill-in marks.** Checkmark, Cross, Dot, and Today's Date are the `mark` tool (`setMark` in `useViewerTools`): the editor mode is `SIGNATURE` for the shapes and `FREETEXT` for the date, and `attachMarkPlacement` (`src/lib/markPlacement.ts`) takes clicks on an empty editor layer in the capture phase so pdf.js never sees them. Shapes are created with `layer.createAndAddNewEditor` and the same `signatureData` saved signatures use: one filled contour per mark (`markShape` in `src/lib/marks.ts`, each corner doubled so pdf.js's curve smoothing keeps it sharp), saved as vector ink with the mark's name as its description. pdf.js keeps a 3 pt margin inside a signature's height, so `heightInPage` adds it back or small marks shrink to nothing. The date makes a FreeText editor at the click, types `dateLabel` into it with `insertText`, and commits it, so it uses the Text tool's remembered color and size and saves as real text. `dateLabel` keeps the reader's day/month order with a four-digit year and falls back to ISO when the locale's digits aren't WinAnsi. Leaving the mark's editor mode (another tool, Esc, a new document) clears the mark.
- **Sticky notes.** `/Text` annotations that aren't replies are taken out of pdf.js's annotation layer (the `AnnotationLayer.prototype.render` wrapper in `pdfjs.ts`, `isStickyNote`) and drawn by `src/lib/stickyNotes.ts` as buttons in a `.sticky-notes` layer on each page div, above the editor layer, so they stay visible and clickable in every tool. Like the diff layer, it's re-attached on `pagerendered`, `scalechanging`, and `rotationchanging`, since pdf.js's `reset()` removes unknown children. A page's notes come from `pdfPage.getAnnotations()` when it renders, and all of them from `getAnnotationsByType` when the Comments list opens. Each note is a `CommentTarget`, so it shares the comment popup and dialog with pdf.js's own comments. Changes live in the document's `annotationStorage` under `clumsy-note:<id>` keys (`notesIn`, `visibleNotes`, `changedNote` in `src/lib/notes.ts`): new notes, edited text, and deletions of notes from the file. Storage makes the tab read as edited, the worker ignores keys it doesn't know, and every change goes on pdf.js's undo stack through `uiManager.addCommands`, so Edit > Undo and the undo bar reach it. Storage values are replaced (remove, then set), never merged, because `setValue` mutates the stored object in place and undo keeps the old one. `viewer.save()` hands pdf.js's saved bytes, those changes, and the markup changes (see Markup) to `writeAnnotations` (`src/lib/notesPdf.ts`), which writes both in one pass: which appends an incremental update with `@cantoo/pdf-lib` (`forIncrementalUpdate`, `commit`), or rewrites the whole file when the old `startxref` doesn't point at an xref (`hasXrefAt`), since pdf.js reconstructs such a file and would keep the old page dictionaries over an appended update: a new `/Text` note (`/Name /Comment`, flags Print, NoZoom, NoRotate) with its `/Popup`, new `/Contents` (dropping its stale `/RC`) when a note's text changed, a new `/Rect` when it moved (its `/Popup` shifts by the same amount), and `/M` on any change, or a note and its popup removed from `/Annots`. It edits `/Annots` directly, because pdf-lib's `addAnnot` normalizes the page and wraps its content streams. Every save path (Save, moving a tab, page edits, restart sessions) goes through `viewer.save()`, so notes are always written, and saving again rewrites them over pdf.js's fresh output. In Comments mode a click on empty page space (the editor layer itself) opens the comment dialog there, and the note's top-left corner lands on the click. Dragging a note (pointer-captured on its button, past a 4 px threshold, clamped to the page) moves it in any tool; the drop's top-left corner goes through `convertToPdfPoint` and `movedNote`, as one undoable change, and the click that follows a drag is swallowed so it doesn't open the popup. If a popup was pinned or an editor selected at pointerdown, that click only closes or deselects it. `writeAnnotations` runs in the page-edit worker (`annotations` job, `writeAnnotationsOffThread`). When pdf.js's saved bytes are encrypted (`hasEncryptEntry`, or an `EncryptedPDFError` from the incremental load), it loads them with the document's password (`passwordOf`, or `""` for owner-only files) and writes the notes as a full, decrypted rewrite; Save encrypts it again for a protected tab, and an owner-only file loses its restrictions.
- **Markup.** Shapes (rectangle, ellipse, cloud, line, arrow), underline, strikethrough, and stamps are Clumsy's, like sticky notes: pdf.js 6.4.299 has no editors for them, can't write them, and turns any `/Stamp` into an image `StampEditor`. The model is `Markup` in `src/lib/markup.ts` (kind, a normalized `box` in PDF user space, `line` endpoints, `quads`, stroke `color`, `fill`, `width`, `opacity`, `dash`, line `endings`, `stamp` id, review `stampDate`, page `rotation` at creation). Changes live in `annotationStorage` under `clumsy-markup:<id>` keys, replaced never merged, each one an undoable command through `uiManager.addCommands` (`commit` in `markupLayer.ts`), so Edit > Undo and the undo bar reach them and the tab reads as edited; Delete shows "Markup removed" in the undo bar. New markup ids are `markup-<uuid>`; markup from the file uses pdf.js's `<num>R` id. **Claiming.** The `AnnotationLayer.prototype.render` wrapper in `pdfjs.ts` drops every Square, Circle, Line, Underline, and StrikeOut that isn't a reply (`isClaimedShape`), from any app, so pdf.js makes no popups or editors for them. Clumsy's own stamps carry `/Name /Clumsy:<stamp id>`; pdf.js doesn't expose `/Name`, so the wrapper awaits `claimStamps`'s provider (the file's markup) whenever a page has a stamp and passes those with `isEditable: false`. They stay in the layer on purpose: in an editing mode pdf.js draws an editable stamp on its own canvas inside its layer element, and `isEditable: false` is what keeps it from becoming a `StampEditor`. Other stamps are left to pdf.js. pdf.js's annotation data lacks `/IC`, `/BE`, `/BS`, `/RD`, and `/Name`, so when a rendered page has any annotation that might be markup (`mayBeMarkup`), the layer reads every claimed annotation in the file once with pdf-lib in the page-edit worker (`readMarkup` job, `readMarkupOffThread` on `pdfDocument.getData()` with the tab's password; `markupFromDict` in `src/lib/markupPdf.ts`). Files without any pay nothing. Comments on claimed shapes from other apps no longer show a popup in Clumsy (phase 2 of `docs/markup-plan.md`); they're kept in the file. **The layer.** `attachMarkup` (`src/lib/markupLayer.ts`, created in `editorManagers.attachViewer`) draws an `svg.markup-layer` on each page div (z-index 2: above the editor layer, below sticky notes), re-attached on `pagerendered`, `scalechanging`, and `rotationchanging`, with one group transformed by `viewport.transform` so every shape is drawn in PDF user space and stroke widths scale with zoom. Markup from the file that hasn't changed only gets an invisible hit target (the canvas draws it); new and changed markup is drawn by `markupDrawing` (`src/lib/markupSvg.ts`) from the same geometry the appearance streams use (`src/lib/markupShapes.ts`, `stampSymbols.ts`), so the two can't drift. Unfilled shapes take clicks only on their stroke (`pointer-events: stroke`, at least 6 px wide), so text inside a big rectangle still selects; filled shapes and stamps take clicks on their area, and underlines and strikeouts only on their line, so text under them still selects in Select. The container's `markup-select` class turns hit targets on in Select (pdf.js mode NONE without the hand) and in the Shapes and Stamps tools; `markup-drawing` adds the page-wide `.markup-surface` that takes drags. Other tools, including the Underline and Strikethrough modes, leave the layer inert. Selection shows a dashed outline and corner handles (end handles for lines) in screen pixels; drag moves (clamped to the page, `clampShift`), a handle resizes (`resizedMarkup` in `src/lib/markupDraft.ts`, Shift keeps proportions, stamps always do), arrow keys nudge 1 pt or 10 pt with Shift in screen directions (`nudgeDelta`), Backspace/Delete removes, Esc deselects. The window `keydown` listener (capture) only acts while focus is inside this viewer's container (pressing on markup focuses it), so a thumbnail's Backspace or another pane's arrows never reach a selection elsewhere, and leaves keys alone in text fields, with a sheet or a `popover` open, and in hidden tabs. Nudges, and restyles of the same properties, within a second of each other are one undo step (`undoBursts` in `markupDraft.ts`, pdf.js's `overwriteIfSameType` with `keepUndo`), so dragging the opacity slider doesn't flood the stack. Drawing and resizing stop at the page edge (`insidePage`), and a shape that comes out under 1 pt wide or tall isn't created (`drawable`). Changing a toolbar style with markup selected restyles it (`restyle`); otherwise the change is remembered in `clumsy.markupParams` (`useMarkupControls`, `src/lib/markupParams.ts`), which `hooks.style()` reads for new markup. **Hiding the canvas copy.** When markup from the file changes, Clumsy draws it and pdf.js must stop drawing the original. pdf.js's display renders with `AnnotationMode.ENABLE_FORMS` never send `annotationStorage` to the worker, so a `noView` storage entry alone does nothing. `hideAnnotations` (`src/lib/hiddenAnnotations.ts`) wraps the document's `_transport.getRenderingIntent` so that non-print intents carry a small storage map of `{ noView: true }` per edited id (the worker's `Annotation.mustBeViewed` checks it first) and a cache key that changes with the set; then `syncHidden` resets just the affected page views (keeping every layer and the old canvas until the new one draws) and calls `viewer.update()`. The map exists only in rendering intents, so nothing reaches Save; thumbnails and the Document Map render without the hidden annotations but also without Clumsy's layer, so unsaved markup isn't in them (as with sticky notes and pdf.js's own unsaved editors). **Tools.** Shapes (`shapeRectangle`… `shapeArrow`, the toolbar's Shapes split button, last shape remembered) and Stamps (`toolStamp` opens `StampPicker`; picking one arms the stamp tool: click places a default size, 36 pt icons or 40 pt-high review stamps, drag sizes it with its aspect) are `MarkupTool`s in `useViewerTools` (`setMarkupTool`): pdf.js mode NONE plus the layer's tool, cleared when any pdf.js mode starts or another tool is picked. Review stamps take today's `dateLabel` and their own color. Underline and Strikethrough are text modes in the Highlight dropdown (`toolUnderline`, `toolStrikeout`; the Highlight button activates the last mode, remembered as `textMode`): mode NONE, and each `pointerup` with a selection in this viewer's text layer becomes markup (`applyText`); Underline/Strike Through Selected Text (Tools menu, right-click selected-text section) do it once. Quads come from the selected text nodes' client rects (`selectedTextQuads` in `src/lib/markupSelection.ts`, skipping `.endOfContent`), grouped by each span's own text direction (pdf.js's `--rotate` on the span, in unrotated page space, `textTurns`), merged per line in that direction (`quadsFromRects`), and written with corners in text order (top-left, top-right, bottom-left, bottom-right), one markup per page, all in one undoable change. The page's `/Rotate` says nothing about the text: a `/Rotate 90` page can hold text that reads upright on screen or text that runs down it. Reading other apps' quads (`orientedQuads`) trusts the first edge's direction, which both conventions (Z order and the spec's counterclockwise order) run along the text, and only falls back to the page's `/Rotate` when that edge is the short one along the page's text axis (quads written as plain boxes). Shapes and Stamps are context tools (`square.on.circle`, `seal` in `context_menu.rs`'s symbol allowlist). **Writing.** `applyMarkup` (`src/lib/markupPdf.ts`) runs inside `writeAnnotations`, so markup follows the notes rules: one incremental update, or a full rewrite when the old `startxref` is bad or the bytes are encrypted. New markup gets a fresh dictionary pushed onto the page's `/Annots` (never `addAnnot`): `/Square` (clouds add `/BE << /S /C /I 1.5 >>`), `/Circle`, `/Line` with `/L` and `/LE`, `/Underline`/`/StrikeOut` with `/QuadPoints`, `/Stamp` with `/Name /Clumsy:<id>`, `/Rotate` for a rotated page, and `/ClumsyDate` for a review stamp's date; plus `/Rect` (the box padded by `outsetOf`), `/RD` for shapes, `/P`, `/NM`, `/C`, `/IC` when filled, `/CA`, `/BS`, `/F 4`, `/M`, `/CreationDate`, `/Subj`, and `/AP /N`. Every appearance (`addAppearance` in `src/lib/markupAppearance.ts`) is a form XObject with `/BBox` equal to `/Rect`, drawn in page space with pdf-lib's `drawSvgPath` (a `[1 0 0 -1 0 0]` matrix cancels its y flip) and two ExtGStates: `GS` (stroke and solid fill at the opacity) and `GF` (fill at `fillAlpha` of it: 30% for fills Clumsy creates, saved as `/ClumsyFillAlpha` so it survives reopening; 1 for another app's fill, so moving a white cover box never makes it see-through). Clouds are cubic Béziers built directly (`cloudPath`), because pdf-lib turns SVG quadratics into inexact `v` curves; Lucide paths are normalized when generated, because pdf-lib can't parse packed arc flags. Stamps draw their design (24×24 grid for icons and electrical symbols, a word-wide grid for review stamps) through `stampMatrix`, which also turns them upright for the page's `/Rotate`, with WinAnsi labels in a non-embedded Helvetica-Bold. Markup from the file that changed has its own dictionary rewritten in place: geometry, `/C`, `/IC`, `/CA`, `/BS` (other `/BS` keys kept, so a dash survives), `/M`, and a regenerated `/AP`; every other key (`/T`, `/Contents`, `/Popup`, `/RC`, custom keys) stays, and its `/Popup` moves with it. Deleting removes it, its `/Popup`, and every reply (`/IRT`, transitively) from `/Annots`. Electrical and icon ids are saved state in `/Name`: never rename one. Printing already uses `viewer.save(true)`, so unsaved markup prints; Export Pages as Images and Print's image fallback render from saved bytes when there are Clumsy-owned changes (see Pages as images). `markupFromDict` skips annotations that are hidden, NoView, ReadOnly, or Locked, and dimension lines (`/Measure`, `/IT`, `/Cap true`, or a leader `/LL`/`/LLO`), whose captions and leaders Clumsy can't redraw; pdf.js keeps drawing them. It reads `/C []` as no border (width 0), `/Border`'s dash array, and every quad as its axis-aligned box (pdf.js does the same), since files order quad corners either way.
- **Editor options.** pdf.js applies `switchannotationeditorparams` to the selected editors when there are any, otherwise to the class defaults, which are static and shared by every viewer in the window. The toolbar shows the selected editor's values (from `annotationeditorparamschanged`) or the remembered ones (`clumsy.editorParams`), and only remembers changes made with nothing selected. Remembered values are pushed whenever an editor mode turns on with nothing selected; pdf.js fires the mode event after it selects a double-clicked editor, which is why the push checks the selection. pdf.js keeps consecutive Draw strokes in one open drawing session and restyles the whole session when a default changes, so `setEditorParam` first ends any session (`commitOrRemove` on each page's editor layer) and unselects the drawing pdf.js selects as it commits, so the change only applies to later strokes. Controls that take focus (the color input, the sliders) would end the session through the editor layer's `blur` listener first, leaving the drawing selected so the change restyles it, so the tools group also ends it on `pointerdown` (`endDrawing`). The session state is static on pdf.js's `DrawingEditor`, shared by every viewer in the window, so a viewer ends its session when it unmounts; otherwise the next tab's strokes go into the closed tab's layer and nothing shows. pdf.js's editor layer also ignores a pointerdown when its previous pointerdown never got a pointerup on the layer itself (a stroke released off the page), which swallowed the next stroke, so in Draw mode a capture-phase pointerdown first sends the layer a non-bubbling `pointerup` to clear that flag. `HIGHLIGHT_FREE` isn't settable: pdf.js draws a freehand highlight whenever a highlight drag starts off text, so only its thickness is offered.
- **Find.** `PatternFindController` runs regular expressions against pdf.js's page text, which is NFD-normalized. Unless Match Diacritics is on, combining marks (except the ones pdf.js keeps, such as viramas) are stripped from both the pattern and the page text, matched, and mapped back so a match covers its accents. With it on, the pattern is NFD-normalized and matches that would end before a mark are dropped.
- **Caret browsing.** WebKit draws no caret in non-editable text, so `src/lib/caretBrowsing.ts` draws one (`.caret-mark`) at the selection's focus and handles the keys itself: Left/Right through `Selection.modify` (⌥ by word), Up/Down by finding the nearest text-layer box on the next line (`nextLine` in `src/lib/caretLines.ts`, continuing to the next page) and the character offset under the caret's x, Home/End to the ends of the line's boxes. Shift extends. Keys inside the annotation and editor layers (a selected drawing being nudged) are left to pdf.js. It's on per window (`clumsy.caretBrowsing`) and only in the focused pane's active tab, so turning it on doesn't move a selection in another pane.
- **Context menu.** Right-clicking a document shows a native `NSMenu` built in Rust (`src-tauri/src/context_menu.rs`, `show_document_menu`), not Tauri's JS menu API, which can't draw a row of icons and whose icons aren't template images. `src/lib/documentMenu.ts` (pure, tested) turns the click into a spec: a palette of tools, then sections (selected text, link, Add Comment Here, Go Back/Forward with the Zoom submenu, and the page section headed "Page 12" or "3 Pages"); empty sections are dropped, and between pages only the navigation section is left. The thumbnail menu is that same page section (`pageSection`), so the two can't drift. The palette is a submenu with `NSMenuPresentationStyle::Palette` and `SelectOne`, which AppKit shows inline as a row; its images are SF Symbols (template images, so they follow dark mode and the selection highlight), allowlisted in Rust (`SYMBOLS`). Rust pops the menu up in the `WKWebView` at the click point (flipping y if the view isn't flipped), points every item at a `ClumsyMenuTarget` that records the item's tag, and returns the chosen id once the menu closes, so nothing goes through Tauri's app-wide menu id map. Copy is a plain `copy:` item aimed at the first responder, so WebKit copies its own selection; Copy Link (`copyText`) writes to `NSPasteboard` in Rust, since the webview's clipboard access needs a user gesture that's gone by the time the menu closes. Off macOS, or if the command fails, `showDocumentMenu` in `platform.ts` falls back to Tauri's JS menu with the palette as ordinary items (`flattenMenu`). `useDocumentMenu` listens for `contextmenu` in the capture phase and leaves inputs, text areas, selects, anything `contenteditable` (a text box being typed in), and comment popups to WebKit's own menu. Right-clicking text makes WebKit select the word under the pointer before `contextmenu` fires (as in Safari), so the text section appears then. The pane you click is already focused by `PaneGrid`'s pointerdown, so commands run on that tab. **Explicit page targets:** page commands act on what the menu says, not on "the selection or the current page," because the page you right-clicked usually isn't the current one and selecting it would scroll. `runCommand(id, { pages })` hands the pages to `runPageCommand`, `runExportCommand`, `runPrintCommand`, and `editPageLabels`; Insert Pages from File inserts after the last of them. The rule is the thumbnails' (`targetPages`): the selection if the clicked page is in it, otherwise that page alone, and right-clicking a thumbnail no longer selects it. Print with explicit pages uses them as given rather than waiting for a running page edit to settle first. Rotating pages keeps the view where it was (`keepPlace` in `usePageEdits`'s `show`), since rotation doesn't move pages; other edits still go to their result's first page. Add Comment Here calls `addNoteAt` on the sticky-note layer (the same path as clicking empty space in Comments mode) and is left out for encrypted files (`canAddNote`). Internal links are followed by clicking the anchor, which runs pdf.js's own handler. **Tools row:** right-clicking a tool on the toolbar offers Add to / Remove from Context Menu and Reset Context Menu Tools. The choice is `clumsy.contextTools` (`src/lib/contextTools.ts`), read when a menu opens, so every window sees changes without a `storage` listener; unknown ids are dropped and the row always follows toolbar order. Fill In places the last-used mark. In Draw mode, the capture-phase pointerup that clears pdf.js's stale pointer flag only fires for the primary button, so a right-click doesn't touch the stroke in progress.
- **Commands, shortcuts, and menus.** `src/lib/commands.ts` is the single source of truth: every command's id, label, menu, and key combos. The same table builds the native menu bar (`src/lib/menu.ts`, via Tauri's JS menu API, so the menu shows each shortcut), resolves keyboard shortcuts in `App.tsx`, renders the Keyboard Shortcuts sheet (⌘K or ⌘/), and fills the Command Palette (⇧⌘P). Every path ends in `runCommand(id)` in `App.tsx`. The layout follows VS Code's defaults where a PDF viewer has an equivalent (⌘B sidebar, ⇧⌘E thumbnails, ⇧⌘O outline, ⌘N new tab, ⇧⌘N new window, ⌘P Print, ⌥⌘P Go to File (VS Code's ⌘P, moved for the standard Print key), ⌃G Go to Page, ⌘↑/⌘↓ first/last page, ⇧⌘T reopen closed tab, ⌥⌘S Save All); keep it that way when adding commands. `⌘1`–`⌘8` stay as Show Tab N, not focus pane. Go Back/Forward use VS Code's macOS keys (⌃- / ⌃⇧-); `ctrl` combos only exist on macOS, so other platforms will need their own (VS Code uses Alt+←/→). Function keys (F7) are menu accelerators even without a modifier, since they never type text. To add a command: add it to the table, place it in `menuLayout` if it belongs in a menu (the tests check every menu command is placed exactly once and no combo is used twice), and handle it in `runCommand`. Combos use physical keys (`event.code`), so ⌥ shortcuts work even though Option changes the typed character. Plain-letter combos (`h`, `n`, `Home`) are ignored while typing and never become menu accelerators, because a native accelerator swallows the key everywhere, including text fields. Combos that move the caret (`movesCaret`: arrows, Home, End with no modifier, ⌘, or ⌥, plus ⇧) are also ignored by the keydown router while typing; ⌘↑/⌘↓ are still menu accelerators, so when one comes from the native menu (`runCommand(id, { fromMenu: true })`) while a field with a caret has focus (`hasCaret`), it moves that caret to the start or end (`moveCaretToEdge`) instead of changing pages. A click on the menu item does the same, since Tauri can't tell it from the accelerator; the palette always changes pages. The keydown router turns Escape into a `cancel` event on the open `<dialog>` (the one holding focus, else the last one opened) and closes it unless a handler prevents that, because WKWebView never cancels a modal dialog on Escape by itself; every sheet's `onCancel` handles it. It ignores IME composition keys. Commands that only work with a split set `needsSplit` (disabled in the menu, hidden from the palette). Scroll and spread modes are check items driven by `checkedCommands` in `menu.ts`, one checked per group like a radio. Native check items toggle themselves on click, so clicking the already-checked mode would uncheck it with no state change to redraw it; their action re-checks the clicked item. Typing `:` and a page number or label in the Command Palette or Go to File offers a single "Go to page" item (`pageJumpItem`). The Command Palette lists every menu command available right now; Go to File (⌥⌘P) lists this window's open tabs and then recent files. Both are one in-window modal `<dialog>` (`QuickPick`) with a fuzzy matcher (`src/lib/fuzzy.ts`). Closing it blurs its input before running the picked command: WebKit leaves focus on an input inside a closed `<dialog>`, which made palette Undo/Redo act on the search field. Closing a tab that has a path remembers it and its view (page, zoom, scroll) for Reopen Closed Tab, per window, up to 20. Native menu accelerators win over the webview's keydown, which is why Undo/Redo are custom items that route to the focused text field or to pdf.js's `editingaction` event; the predefined Undo would never reach pdf.js. Document commands set `needsDocument` and are disabled in the menu when the active tab has no PDF. Those that also make sense for a Markdown tab add `markdown: true`, and Markdown-only commands (Markdown Source) set `needsMarkdown`; `documentAvailable` decides all three for the menu, the palette, and `runCommand`. The Rust side no longer builds menus.
- **Windows and dialogs.** Document windows are the only Tauri windows. About (with its What's New and Licenses tabs) and Keyboard Shortcuts are in-window `<dialog>` sheets in each document window (`AboutDialog`, `ShortcutsDialog`), held as one `infoSheet` state in `App.tsx`, so only one shows at a time. ⌘K toggles Shortcuts; Esc, Done, Close Tab, and Close Window close whichever is open before doing anything else. Rust and `documentWindows.ts` treat only `main` and `doc-*` as windows; new window labels must be added to `capabilities/default.json`. Questions with only buttons use native alerts (`@tauri-apps/plugin-dialog`, see `src/lib/defaultAppPrompt.ts`). The password, signature, alt text, comment, and export prompts need inputs, so they're in-window `<dialog>`s styled as sheets (`.dialog.sheet`), like About and Shortcuts.
- **Title bar.** The window uses `titleBarStyle: Overlay` with `hiddenTitle`; the toolbar pads left for the traffic lights (except in fullscreen) and toolbar groups carry `data-tauri-drag-region`.
- **Third-party licenses.** `pnpm build` (and so every release) runs `scripts/third-party-licenses.mjs`, which collects license texts for the npm packages the UI bundles (production `dependencies`, walked transitively) and the Rust crates compiled into the binary (`cargo metadata`, normal dependencies only). For "A OR B" licenses it uses MIT when offered. Crates that ship without a license file get the shared Apache/MPL text or an MIT/BSD template with the crate's authors. Identical texts are listed once. The About sheet shows the result under Licenses. New dependencies are picked up automatically; check the "without a bundled license file" section of the output if a new license type appears.
- **Updates.** Two halves. Finding out about a release and showing its notes is still the GitHub releases API (`src/lib/updates.ts`, `useUpdatePrompt` in `main` only, every 6 hours and on focus; About > Check for updates in any window), because it can list every release since the running one. Installing goes through `tauri-plugin-updater`, called only from Rust: `install_update` (`src-tauri/src/updates.rs`) checks `latest.json` on the latest GitHub release, downloads `Clumsy.app.tar.gz` with progress over a `Channel`, verifies its minisign signature against `plugins.updater.pubkey`, and swaps the `.app` bundle in place (it asks for an admin password through AppleScript when the bundle isn't writable). `requireSignedVersion` is on, so the signature must name the version the manifest announces, which stops a replayed old release. The plugin's own JS commands aren't in the capabilities; the webview can only ask Rust to install whatever the configured endpoint offers. It refuses outside an installed `.app` (dev builds) and from a translocated copy (run from Downloads or the disk image), and the UI falls back to Download, which opens the release page. One install runs at a time across windows, requests time out after 10 minutes, and a version already installed in this process isn't downloaded again. Later and Esc close the Update sheet while a download runs (About keeps showing its progress); a failure offers Try Again and Download. The running process keeps the old version until Restart Now, which restarts with the session kept (below) through `AppHandle::restart`, which relaunches the bundle through LaunchServices. `useUpdateInstall` holds the install state per window, shared by the Update sheet and About.
- **Restart sessions.** Restart Now (`request_restart`, `src-tauri/src/session.rs`) emits `capture-session` to every document window and waits up to 30 seconds for each to answer `report_session`. Each capture has an id, sent with `capture-session` and checked on `report_session`, so a late answer to an abandoned capture can't count toward a new one. `useRestartSession` captures a window with `captureTab` (shared with moving tabs between windows, so pending page edits settle first): saved files go by path and view state, while unsaved or pathless tabs bake their markup into bytes through the transfer stash, exactly like a tab move, so they come back with `carriedChanges` and lose only their undo history. Panes keep their order, sizes, active tab, and focus; windows keep their bounds, and the last focused window is focused again. Rust only keeps paths the window was actually given (`AllowedPaths`, or `ReadOnlyPaths` as read-only, which stays read-only after the restart), so a page can't use a restart to widen its file access. A refused path drops a saved tab, but an unsaved one keeps its bytes and comes back pathless (Save asks where to put it), since its folder may simply have moved. When every window has answered, Rust writes `restart-session/` (0700) in app data and restarts, deleting the folder again if the write fails; the next launch reads it, deletes it, restashes the bytes, allowlists the paths, and skips the command-line files the relaunch repeats. `main` opens one window per extra saved window (`?restore=N`) and each takes its own entry once (`take_restored_window`); `restored_windows` lists only entries not yet taken, so reloading `main` doesn't reopen windows. Restoring moves and resizes windows, which needs `core:window:allow-set-position`/`allow-set-size` in the capabilities. If a window fails to capture or times out, or writing fails, it falls back to `confirm_quit` with `restart: true`, the old "Discard and Restart" alert. A protected tab's bytes are encrypted before they're stashed (`bytesForDisk`) and its password is never written, so after the restart it asks for its password once; the restart folder is on disk, and neither a protected document's plaintext nor its password belongs there. A tab that can't be reopened is skipped with one error listing its name. Comparisons, find, and sidebar panels aren't kept. Quitting doesn't save a session. Known gaps: edits made in a window after it has answered but before the last window does aren't in the session, and the folder is deleted as soon as the next launch reads it, so a crash before the windows finish restoring loses what it held.
- **Version** shown in the app comes from `tauri.conf.json` at build time (`__APP_VERSION__` in `vite.config.ts`). CI runs `scripts/set-version.mjs` so `package.json`, `tauri.conf.json`, and `Cargo.toml`/`Cargo.lock` all match the release, then commits them with the stamped changelog.

## Releases

Every push to `main` builds, signs, notarizes, and publishes a GitHub release (`.github/workflows/release.yml`). Pull requests run `ci.yml` instead.

- **Versioning** (`scripts/next-version.mjs`): the bump comes from the changelog, so nobody picks version numbers. If `[Unreleased]` has an entry under `### Added`, the release bumps the minor of the latest `vX.Y.Z` tag (0.4.2 → 0.5.0); otherwise it bumps the patch (0.5.0 → 0.5.1). Feature branches and parallel sessions never edit version numbers: they only add entries under the right heading, and whatever has landed on `main` when the release runs decides the bump. Use `### Added` for new capabilities (commands, menu items, file formats, tools), not for improvements to existing ones, which go under `### Changed`. Major versions are manual: set `version` in `src-tauri/tauri.conf.json` (for example `1.0.0`); a version there that's ahead of the latest tag is released exactly, and later pushes continue from it. Don't hand-edit `package.json` or `Cargo.toml` for releases — the workflow keeps them in sync.
- **Changelog**: add user-facing changes under `## [Unreleased]` in `CHANGELOG.md` (Keep a Changelog sections: Added / Changed / Fixed / Removed; `**bold**` renders in the app). On release, the workflow moves those entries under `## [x.y.z] - date`, builds with the stamped file so What's New is correct, uses that section as the release notes, then commits the changelog and version files back to `main` as `Release vx.y.z`. If `[Unreleased]` is empty, the notes list commit subjects instead, but the version files are still committed.
- **If you've edited `CHANGELOG.md` locally while a release ran**, the pull can silently merge your new entries into the just-stamped version section. Check that they're still under `[Unreleased]` after pulling.
- **After every release `origin/main` is one commit ahead** (the version + changelog commit). Run `git pull --rebase` before pushing again, or set `git config pull.rebase true`. Pushes made with the workflow's `GITHUB_TOKEN` don't trigger new workflow runs, so there's no release loop.
- Releases run one at a time (`concurrency: release`). Only pushes that touch the app's build inputs release: `src/`, `src-tauri/`, `public/`, `index.html`, `package.json`, `pnpm-lock.yaml`, `vite.config.ts`, or `tsconfig*.json`. Docs, `web/`, `scripts/`, `tests/`, `CHANGELOG.md`, and workflow edits alone don't; they ship with the next release. Pull request CI uses the same filter plus `tests/` and `ci.yml`. The workflow can also be run manually from the Actions tab.
- Assets are `Clumsy.dmg` and `Clumsy.zip`: universal (Apple Silicon + Intel), Developer ID signed, notarized, and stapled. Each release also carries `Clumsy.app.tar.gz` and `latest.json` for in-app updates (see Signing).

Team ID `M3C8F32WA5`; identity `Developer ID Application: Texas Beard Company LLC (M3C8F32WA5)`.

Updates are signed separately with a Tauri (minisign) key: `TAURI_SIGNING_PRIVATE_KEY` (the contents of `~/.tauri/clumsy-updater.key`) and optionally `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`; the public half is `plugins.updater.pubkey` in `tauri.conf.json`. After notarizing and stapling, the workflow tars the stapled `.app` into `Clumsy.app.tar.gz` (`COPYFILE_DISABLE=1`, the bundle at the archive root), signs it with `tauri signer sign --app-version`, and `scripts/update-manifest.mjs` writes `latest.json` (the same universal archive for `darwin-aarch64` and `darwin-x86_64`). Check a password with `/usr/bin/openssl pkcs12 -in <file> -nokeys -clcerts | /usr/bin/openssl x509 -noout -subject`. Use macOS's LibreSSL; Homebrew's OpenSSL 3 rejects Keychain's legacy encryption and looks like a wrong password.

## Website

`web/` is the marketing site: React Router 8 with SSR on Netlify (`@netlify/vite-plugin-react-router`), the same stack as the DutiHEHE and TheAnnex sites. It's its own pnpm package with its own lockfile, not a workspace, and needs Node 22.22+ (`web/.node-version`), while the app itself builds on Node 20. Plain CSS in `app/app.css` with tokens on `:root`; the colors are the icon's orange-to-pink gradient on the dark background of the tour videos.

```bash
cd web
pnpm install
pnpm dev                       # http://localhost:5173
pnpm typecheck
pnpm build                     # client assets in build/client, the server function in .netlify/
```

- **Content comes from the repo, at request time.** `/` and `/changelog` are rendered by the server function on each request. Their loaders (`app/lib/releases.server.ts`) fetch `CHANGELOG.md` from `main` on raw.githubusercontent.com (3 s timeout, kept for 10 minutes per function instance) and parse it with the app's own `src/lib/changelog.ts`; Unreleased is left out, and the newest released section is the version shown on the home page and footer (the root loader, read with `useVersion`). The home page's feature lists and shortcuts come the same way from `web/content/features.json` (`app/lib/features.server.ts`), checked by `toSiteContent` (`app/lib/siteContent.ts`, tested in `siteContent.test.mjs`): a file that doesn't parse or is missing a field is ignored, and only known fields reach the page. Edit that file and push to change them; the screenshots and their captions stay in `app/lib/content.ts` because they go with images. If a fetch fails, the copy bundled at build time is used (the build fails if the bundled `features.json` is malformed). The fetch helper is `remoteContent` in `app/lib/remote.server.ts`. Responses carry `Netlify-CDN-Cache-Control: public, durable, s-maxage=600, stale-while-revalidate=86400` (and `Cache-Control: max-age=0` for browsers), so the function runs about once per 10 minutes per page, and a release or a content edit shows on the site within about 10 minutes of reaching `main` without a deploy. Every deploy costs Netlify credits, so Netlify's `ignore` command builds only when `web/` (other than `web/content/`) or the parser changed.
- **Downloads.** `/download` is a Netlify redirect to `releases/latest/download/Clumsy.dmg`, so buttons never name a version.
- **Media.** Every screenshot in `web/public/screenshots/` is a `<name>-light.webp`/`<name>-dark.webp` pair that `ThemeSlider` shows split by a draggable divider (pointer drag, or arrow keys on its hidden range input). Each pair is one `pnpm dev` session in headless Chrome captured twice with only `prefers-color-scheme` emulation changed, so the halves line up pixel for pixel; recapture both whenever one changes. `web/public/media/` holds a copy of the newest tour (git stores the identical file once). Replace them when a new tour ships.
- **Netlify.** The site is `clumsyapp` (https://clumsyapp.netlify.app) on Ryan's personal Netlify team, built from Git with base directory `web`; `netlify.toml` has the build command, publish directory, Node version, redirect, and cache headers. Absolute `og:image` URLs use Netlify's `URL` build variable (`__SITE_URL__`). Nothing is prerendered; `routeDiscovery` is `initial`, so the client never asks the server for route manifests. Don't deploy with `netlify deploy` from `web/`: the CLI treats the repo root as the project root and ships the site without its server function (or without its routes), and leaves an empty `.netlify/` at the root. The dev server turns off Netlify's edge-function emulation, which fails with recent Deno and isn't used.

## Conventions

- Never commit test documents. `public/` is copied into the app bundle, and `public/*.pdf` is git-ignored for that reason; keep sample PDFs outside the repo. Review `git status` for new files before every commit instead of blindly staging everything.

- Match the existing style: no code comments unless the logic truly needs one, self-explanatory names, small pure helpers in `src/lib` with vitest coverage.
- Heavy libraries load on first use. pdf-lib is only reached through `import()` (`pageEdits.ts` from `usePageEdits` and `imageImport.ts`, `imagePdf.ts`, `comparisonReport.ts`; sticky notes are written in the page-edit worker), and `TabContents` lazy-loads `MarkdownTab`, which brings markdown-it, highlight.js, DOMPurify, and `Markdown.css` with it (CodeMirror is a further chunk on top). Helpers that callers need synchronously live apart from the library code (`pageEditPlan.ts` holds the page-edit types and page arithmetic), because one static import pulls the whole library back into every window's startup bundle. After `pnpm build`, the main `index-*.js` should hold only pdf.js, React, Tauri's API, and the app (about 1.1 MB).
- Keep source files under 500 lines. When one grows past that, split it along a real seam (a hook, a component, a pure helper in `src/lib`) rather than arbitrarily.
- Global form-control resets use `:where(:is(button, input, select):not(.pdfViewer *))` on purpose: zero specificity so component classes win, and pdf.js's own controls (whose layers set huge font sizes) are left alone.
- `pdfjs-dist` is pinned to an exact version. Upgrade it only by following `docs/pdfjs-upgrade.md`: Clumsy depends on pdf.js internals (manager methods, private fields, event names, Firefox-only CSS variables, worker fallbacks) that types don't cover, `tests/pdfjsContract.test.ts` checks them against the installed sources, and the doc lists what only a built app shows. When you add a new dependency on a pdf.js internal, add it to the doc's inventory and, where it can be read from the source, to the contract test.
- `pdf_viewer.css` is global and styles some bare class names for Firefox's own UI (`.sidebar` gets a radius, border, shadow, and padding), so don't give app elements generic names it may use; the document sidebar is `.app-sidebar` for that reason.
- pdf.js 6 API notes: `PDFDocumentProxy.destroy()` is gone (use `loadingTask.destroy()`); `page.render({ canvas, viewport })`; editor modes are set with `viewer.annotationEditorMode = { mode }`; default colors go through the `switchannotationeditorparams` event.
- WebKit forgets the abort of a signal made by `AbortSignal.any` once that signal is garbage collected, so a listener added with it stays attached after the abort. pdf.js removes its keyboard shortcuts (Backspace deletes the selected editors) and other listeners that way, which left Backspace in a sheet's text area deleting markup. `src/lib/polyfills.ts` replaces `AbortSignal.any` with one built from plain `AbortController`s (`installAbortSignalAny`); Chromium doesn't show the bug, so check it in a built app.
- The webview is the system WebKit, so the oldest Safari engine on a supported macOS sets which JavaScript built-ins exist. macOS 15.4 ships Safari 18.4, which has everything pdf.js 6.4.299 calls (the global `Iterator` and its helpers, `Promise.try`, `Uint8Array` base64/hex, `RegExp.escape`) except `Map`/`WeakMap` `getOrInsert`/`getOrInsertComputed` and `Math.sumPrecise` (Safari 26.2), which `src/lib/polyfills.ts` installs when missing. Raising pdf.js or using a newer built-in means checking it against Safari 18.4 (MDN's browser-compat-data) and either polyfilling it there or raising `minimumSystemVersion` to the macOS that ships the needed Safari. Lowering the floor below 15.4 needs the global `Iterator` before `pdf.mjs` loads, which reads it at module load.
- WebKit can deadlock a thread inside a stream reader: `ReadableStreamDefaultReader` methods hold the reader's lock while running JavaScript, and if that allocation starts a garbage collection, a GC helper thread waits on the same lock forever. pdf.js's worker inflates every Flate stream (nearly every page's content) through `DecompressionStream` read with `for await`, so a fast scroll through a long document froze the worker and every page, thumbnail, and map render with it (a `sample` of the web process shows `releaseLock` → `collectInMutatorThread` on `WebCore: Worker` and a `Heap Helper Thread` in `isReachableFromOpaqueRoots`). `pdfWorker.ts` calls `removeDecompressionStream` (`src/lib/polyfills.ts`), which deletes `DecompressionStream` in WebKit only, and pdf.js falls back to its own JavaScript inflate. The main thread still reads pdf.js's operator-list streams and could in principle hit the same bug.
