# Clumsy

A lightweight PDF viewer built on Tauri. Releases are macOS-only today; Windows and Linux are planned, so keep platform-specific code behind `platform.ts` / `cfg(target_os)` and wording platform-neutral. Tagline: "No tricks, no acrobatics." Avoid naming other companies' products (for example Adobe Acrobat) in the app, README, or store listings. Tauri 2 (Rust) shell, React 19 + TypeScript UI, pdf.js 6 for rendering and markup. Sponsored by Texas Beard Company, the same branding used in TheAnnex and DutiHEHE.

Repo: https://github.com/ry4nolson/clumsy (public, MIT License). The local folder is still named `pdf-viewer`. The license covers code only: the Clumsy name and icon and the Texas Beard Company name and logos are excluded (see README).

## Commands

```bash
pnpm install
pnpm tauri dev                 # run the desktop app with hot reload
pnpm dev                       # browser-only UI at http://localhost:1420 (no file paths, menus, or recents)
pnpm test                      # vitest (tests/*.test.ts)
pnpm exec tsc --noEmit         # typecheck
cargo clippy --manifest-path src-tauri/Cargo.toml -- -D warnings
cargo test --manifest-path src-tauri/Cargo.toml --lib
pnpm tauri build --bundles app # local release build -> src-tauri/target/release/bundle/macos/Clumsy.app
pnpm licenses                  # regenerate public/third-party-licenses.txt (also runs as part of pnpm build)
```

- Node 20.19+ is required by Vite 8 (Node 22 recommended). pnpm is pinned through `packageManager` in `package.json`.
- Universal builds (`--target universal-apple-darwin`) need rustup's toolchain with `x86_64-apple-darwin` installed. Homebrew's `cargo` can't cross-compile, so put `~/.cargo/bin` first in `PATH` for those builds.

## Architecture notes

- **Tabs and panes.** `src/lib/workspace.ts` is the pure, tested model: a map of tabs plus an ordered list of panes (each with its tab order, active tab, and flex size) and the focused pane. Every open document mounts its own `DocumentTab` with its own pdf.js `PDFViewer`; never swap documents inside one viewer, because unsaved highlights and notes live in the viewer's editor layer. `PaneGrid` lays panes out as a CSS grid (row 1 tab strips, row 2 documents, 5px divider columns between panes) and renders every `DocumentTab` as a sibling in one keyed list, positioned by `gridColumn`. That is what lets a tab move between panes without remounting: only its column changes, so scroll, zoom, and unsaved markup survive. Inactive tabs stay laid out but hidden (`visibility: hidden` + `inert`); `display: none` would reset their scroll position. App keeps per-tab `TabSnapshot`s (page, zoom, tool, modified, find state); the focused pane's active tab drives the toolbar, menus, and window title. Tab dragging and divider resizing are pointer-event based in `PaneGrid` (HTML5 drag and drop is unreliable in Tauri webviews); the divider has a widened invisible grab area. At most `MAX_PANES` (4) panes.
- **Document windows.** Every document window (label `main` or `doc-*`) runs the full `App` with its own workspace; `src/lib/documentWindows.ts` opens them, finds the window under a drop point, and hands tabs over; `useTabTransfer` drives it from the app. A live pdf.js document can't move between webviews, so moving a tab calls `saveDocument()` (unsaved markup is baked in), stashes the bytes in Rust (`stash_transfer` / `take_transfer`, raw IPC, taken once), and the receiving window reopens them with the same page and zoom. A tab that arrives with unsaved changes keeps a `carriedChanges` flag so it still reads as edited until saved; undo history from before the move is lost. Each window builds its own app menu and calls `activate()` (`setAsAppMenu`) when it gains focus, because menu callbacks run in the window that built them. Don't give menu items fixed ids: Tauri routes menu clicks through one app-wide id → handler map, so a shared id sends every window's clicks to the newest window. Keyboard shortcuts hide the problem because the focused page handles them first. Rust tracks the last focused document window (`windows.rs`) and sends Finder-opened files there with `emit_to`, which is why `files-opened` is listened for per webview. Each window reports its open paths and unsaved document names to Rust (`report_documents`) whenever they change; opening a path another window already has focuses that window's tab instead (`document_window`, `show-document` event), so one file never has two writers in different windows. The default-app launch prompt only runs in `main`. Closing the last document window also closes About/Shortcuts. Capabilities list `doc-*`. Tab tear-off is detected in `PaneGrid` when a drag ends outside the window; drops onto another window merge into its focused pane.
- **Start tabs.** Opening a file from a Start tab replaces that tab, like a browser's new-tab page. Opening a path that's already open anywhere switches to its tab, except Split Right, which deliberately opens a second copy. Closing the last tab in a pane removes the pane; closing the last tab overall leaves a Start tab.
- **Saving.** `pdfDocument.saveDocument()` writes markup and form values as an incremental update over the original bytes held by the worker, so repeated saves don't duplicate annotations. The Rust `write_pdf` command takes raw bytes with the path in a percent-encoded `x-path` header and writes atomically (temp file + rename, into the symlink's real target, keeping the original permissions), `.pdf` paths only. Each tab keeps the file's stamp (mtime + size) from when it was read; saving to the same path sends it as `x-expected-stamp`, and if the file changed on disk Rust refuses with `changed-on-disk` so the app can ask before overwriting. Saving returns the new stamp.
- **External changes.** `useExternalChanges` polls `file_stamp` for each open file every 2 seconds while the window is visible, and right away when it gains focus. A tab reloads in place (same page, zoom, and scroll, via `viewState()`) only when `canReload` in `src/lib/externalChanges.ts` says so: the stamp changed, nothing is unsaved or carried over from another window, and the draw or text tool isn't active (those can hold edits pdf.js hasn't committed yet). Before swapping, the stamp must hold steady for 300 ms and the new bytes must end in `%%EOF`, so a file another program is still writing isn't loaded half-done. Edited tabs are left alone; Save's changed-on-disk prompt covers them.
- **Page edits.** `src/lib/pageEdits.ts` does the structural work with `@cantoo/pdf-lib` (the maintained pdf-lib fork, which can also encrypt): reorder, delete, rotate, insert another PDF, extract, combine. The low-level page tree work lives in `src/lib/pdfStructure.ts`. pdf.js can't change a document's pages, so every page edit takes the current bytes from `viewer.save()` (unsaved markup is baked in, like moving a tab between windows), rewrites them, and swaps them into the tab as a new `source` with `carriedChanges: true`, keeping zoom and moving to the right page (`pageAfterEdit`). Every edit first flattens the page tree into one `/Pages` node, copying inherited `Resources`/`MediaBox`/`CropBox`/`Rotate` onto each page, and then just rewrites `/Kids`; pdf-lib's own `removePage`/`insertPage` corrupt the tree when every page moves and let inserted pages inherit a branch's rotation. Removing pages (delete, and extract, which removes everything else) also removes their annotations and form widgets, fields left with no widgets (and their `/CO` calculation-order entries), tagged-PDF structure elements whose content was all on those pages (`src/lib/pdfStructTree.ts`, so their `/Alt` and `/ActualText` go too, along with their `/IDTree` entries), links, bookmarks, and an `/OpenAction` that pointed at them (named destinations are resolved through `/Dests` and the `/Names` tree before they're pruned, since LaTeX and many other producers only use names), and named destinations, then nulls any other reference to them. Removing pages also drops XFA form data (pdf.js doesn't render it, and it keeps its own copy of every field value); other edits keep it, because a dynamic XFA form has nothing else. Structure elements reached through two parents are decided once, and an `OBJR` pointing at an annotation is judged by that annotation, not by the element's `/Pg`. Pages copied in from another file lose `/StructParents` so they don't collide with the target's structure tree. Before saving, `collectGarbage` drops every object the trailer can't reach and pdf-lib rewrites the whole file, so a deleted page's content is really gone and no earlier revision survives. That matters: people delete pages to remove private information. Inserted and combined pages are copied by copying the source's (flattened) page tree in one pass, so links between them point at the copies. Their form fields stop being fields, and the first file's fields keep working when combining. Password-protected PDFs are refused with a clear message. Page labels follow their pages: every edit except rotation reads the `/PageLabels` number tree (`src/lib/pdfPageLabels.ts`), maps each label to its page ref, and writes a fresh tree with `encodePageLabels` (`src/lib/pageLabels.ts`) that finds decimal, roman, and letter runs and falls back to a prefix-only range per page. Inserted and combined pages bring their own file's labels, or their new page number when that file has none. A file without labels never gains them.
- **Comparing documents.** A comparison is two tab ids held by `useComparison`; `workspace.ts` knows nothing about it. It ends when either tab closes, leaves the window, or both land in the same pane. `pdfText.ts` reads each page's `getTextContent()` (cached per `PDFDocumentProxy`) and `diffTokens.ts` turns the items into words with boxes in page fractions at the page's own rotation (`getViewport({ scale: 1 })` applies `/Rotate`, so drawing only adds `viewer.pagesRotation`). Items that continue a word are joined, line-end hyphens are joined, soft hyphens dropped, text NFKC-normalized, and content order is kept (no reading-order sort, which would interleave columns). The worker diffs the whole token stream with `diff` (jsdiff's `diffArrays`, 4 s timeout) and falls back to page-by-page (300 ms each, then the whole page counts as changed). `buildComparison` slides pure insertions/removals to start on a line (`slideToLineStarts`), merges word boxes per line, places a thin marker where text is missing on the other side, notes pages that are wholly added/removed or have no text, and records one anchor per matched line for linked scrolling (`syncLocation`). Highlights are DOM in a `.diff-layer` on each page div, never annotations, so nothing reaches Save. pdf.js's `reset()` removes unknown children on zoom and rotation, so the layer is re-attached on `scalechanging`, `rotationchanging`, and `pagerendered`. Linked scrolling remembers the `scrollTop` it set on the follower and ignores that one echo. Recomputes when either tab's `source` changes (page edits, outside reloads, Swap); markup and form typing don't change the text. Each change keeps an 80-character `before`/`after` snippet for the sidebar plus the full `beforeText`/`afterText` and word counts per side. Export Comparison Report (`exportComparison`) lays out a PDF from those in `src/lib/comparisonReport.ts` with `@cantoo/pdf-lib` and its standard Helvetica (WinAnsi only: other characters are NFKD-stripped of accents or drawn as `?`, so no font is fetched or bundled), then saves it through `pick_save_path` + `write_pdf`.
- **Document Map.** `DocumentMap` is a flex sibling of `.viewer-area` in each `DocumentTab` (a pane, not an overlay), on by default and toggled with ⌥⌘B (`clumsy.documentMap`). Its layout comes from the viewer's own page divs (`getBoundingClientRect`, re-measured by a `ResizeObserver` on `.pdfViewer`), normalized by the widest page so zoom doesn't change the map. `layoutMap` in `src/lib/documentMap.ts` fits every page into the pane's height, down to `MIN_PAGE_WIDTH`, then lets the map overflow. The pane's width follows the scaled pages (`layout.width`, at most `MAP_MAX_WIDTH`), so it narrows for long documents; the viewer's fit-width re-fit this causes doesn't feed back, because the layout only depends on the pages' proportions. Viewer and map positions are converted piecewise-linearly between page and gap stops (`toMap`), since the viewer's gaps are fixed pixels at any zoom. When the map overflows, the slider moves linearly with the viewer's scroll ratio and the map content is offset from that, like VS Code; a linear content offset instead makes the slider stall inside pages and jump at gaps. Dragging inverts this with a binary search (`scrollForSlider`). Pages render once at the pane's full width (a one-at-a-time queue per document) and stay rendered after first being near view; rotation re-renders them. Find marks come from pdf.js's `pageMatches`, which index into the concatenated `item.str`s of `getTextContent({ disableNormalization: true })` with no characters for line ends (that's how pdf.js's own highlighter reads them; `rangeRects` in `diffTokens.ts`), and only show while the find controller's `highlightMatches` is on: pdf.js re-sends the full match count after the find bar closes.
- **Page edit timing.** `usePageEdits` keeps per-tab state: a queue (edits run one at a time), the `pending` version (shown but not yet loaded by pdf.js; the next edit starts from it), a `generation` counter, and up to 20 earlier versions, capped at 256 MB in total (`trimHistory`). Commands capture the generation when issued and are dropped if another edit landed first, because their page indices refer to the old version. History belongs to one `source` object: if anything else replaces the tab's source (an outside change reloading the tab), the history is cleared, and an edit whose baseline changed while it was computing is cancelled. Save and moving a tab to another window first `await settled(tabId)`. Save only clears `carriedChanges` if the source it saved is still the tab's source. If pdf.js can't open an edited version, `documentFailed` restores the previous one instead of closing the tab. Undo and Redo are routed by `routeStep`: Undo goes to pdf.js while pdf.js has something to undo (`viewer.editHistory()`, from pdf.js's `editingstateschanged` event, so it survives Save), otherwise to page history, except after the user typed into a form field since this version loaded (`changed`, set by `input`/`change` events inside the annotation layer; typing isn't on pdf.js's undo stack, and page undo would take the typed values with it). Don't use `annotationStorage` modification for this: pdf.js writes to it while rendering radio buttons. Redo goes to pdf.js while pdf.js has something to redo; if markup or typing sits on top of the current version, page redo is cleared instead, because those versions predate it. While an edit is queued or a version is loading, Undo and Redo are queued behind it instead of going to pdf.js. `documentLoaded`/`documentFailed` get the `source` that finished loading and ignore stale ones, so a quick Undo can't clear the wait for a newer version. Selection lives in `DocumentTab` and only counts while it includes the current page (`followCurrentPage`), so scrolling away quietly drops it; commands act on the selection or else the current page. Dragging to the same spot is a no-op (`changesDocument`). Thumbnail drag-to-reorder is pointer based like tab dragging. Dropping PDFs on a visible sidebar inserts them at the drop line (`src/lib/dropTarget.ts`, marked with `data-drop-*` attributes React doesn't manage); dropping anywhere else opens them as before. The thumbnail context menu is a native popup (`showContextMenu`).
- **File access.** The webview can only read or write paths Rust handed out: files picked in Rust's dialogs (`pick_pdf`, `pick_pdfs`, `pick_image`, `pick_save_path`), dropped on a window, opened from Finder or the command line, or in recent files. `files.rs` keeps that allowlist (canonical paths) and `read_pdf` / `read_image` / `write_pdf` / `record_recent_file` check it, so a compromised page can't read arbitrary files. Don't call the dialog plugin's `open`/`save` from JS for files; add a Rust command that allows the result. File IPC commands are `async` so large reads and writes don't block the main thread (sync commands run on it). The CSP lives in `tauri.conf.json`; `devCsp` is `null`, so `pnpm tauri dev` doesn't enforce it. Check CSP changes with a `pnpm tauri build` app.
- **Quitting.** Quit is a custom command (⌘Q), not the predefined item, because the predefined one terminates without any chance to ask. It reports this window's documents (finishing in-progress edits first) and calls `request_quit`, which exits right away or shows one native "Discard and Quit" alert listing every unsaved document across windows. Quitting from the Dock or logging out still skips the prompt: tao doesn't implement `applicationShouldTerminate`.
- **Dark pages.** The default ("Keep images") applies `invert(0.92) hue-rotate(180deg)` to `.canvasWrapper` and the editor layer, then draws each image's original pixels into an unfiltered overlay canvas (`.image-restore`). Image rectangles come from pdf.js's image tracker (`imagesRightClickMinSize: 0`) and are rotated by `src/lib/imageRegions.ts`. pdf.js's own `pageColors` high-contrast mode recolors images too, so it isn't used. `enableDetailCanvas` stays off: pdf.js draws the detail canvas inside `.canvasWrapper`, under the `.image-restore` overlay, and `restoreImages` copies image pixels from the base canvas (it skips detail renders), so at high zoom images would show at the base canvas's lower resolution on top of the sharp detail render. Turning it on means restoring images from the detail canvas too, at its offset.
- **Fit width / fit page on resize.** `usePdfViewer` re-applies preset zooms when the viewer's *border-box* size changes. Don't observe the content box: with always-visible scrollbars the scrollbar appearing narrows the content box, the page re-fits smaller, the scrollbar disappears, and the page loops forever (it shakes and pins a CPU). `.viewer-container` also uses `scrollbar-gutter: stable`.
- **Recent files.** Rust owns the list (`~/Library/Application Support/com.ry4nolson.clumsy/recent-files.json`, max 20, menu shows 10) so the native menu works before the webview loads. The frontend records a path after a successful load or a Save As, and listens for `recent-files-changed`.
- **Default PDF app.** `default_app.rs` calls `LSCopyDefaultRoleHandlerForContentType` / `LSSetDefaultRoleHandlerForContentType` for `com.adobe.pdf` (what `duti` uses). Only offered when running from an installed `.app`; dev builds aren't registered bundles.
- **Scroll and spread modes.** `viewer.scrollMode`/`spreadMode` reset on every `setDocument`, so they're applied in `pagesinit` before the zoom and location, from the tab's `ViewState` if it has one, otherwise the last choice (`clumsy.scrollMode`/`clumsy.spreadMode`, written only when the user picks a mode). They live in `ViewState`, so they survive tab moves, Reopen Closed Tab, outside-change reloads, and page edits. The Document Map lays pages out in rows (`pageRows`: pages whose boxes overlap vertically share a row), which covers spreads and wrapped scrolling. `MIN_PAGE_WIDTH` applies to each page, not the row. In wrapped scrolling the pane stays at `MAP_MAX_WIDTH` and centers its content: how many pages fit in a row depends on the viewer's width, so a pane that followed the layout's width would loop with the viewer (the same shake as fit width). Horizontal and page scrolling hide it, disable its menu item, hide it from the Command Palette, and ignore ⌥⌘B (`documentMapAvailable`), because the map follows vertical scroll. Next/Previous Page and the Space tap use pdf.js's `nextPage`/`previousPage`, which step by spread. `scrollLocation` reports the first page of a row, so linked scrolling follows the left page of a spread. Linked scrolling in a comparison is skipped while either side scrolls horizontally or by page (`CompareView.linkable`), and Next/Previous Change first sets the current page in those modes so `revealRect` has a laid-out page to scroll to.
- **Back and forward.** pdf.js's `PDFHistory` drives `window.history` and assumes one document per page, so each viewer keeps its own stack (`src/lib/navHistory.ts`, at most 50 stops) and plugs an adapter into `linkService.setHistory`: `pushCurrentPosition` records the current `updateviewarea` location before link and outline jumps, and the `GoBack`/`GoForward` named actions step it. Go to Page, first/last page, the palette's `:page`, the first find of a search and every Find Next/Previous, and comparison change jumps record explicitly (`recordStop`, `goToPage(page, true)`); ordinary scrolling and Next/Previous Page don't. Stepping pushes the current spot onto the other stack and scrolls with an XYZ destination, so it survives zoom changes. The stack is part of `ViewState`; page edits remap its pages with `pageAfterEdit` (`remapStops`). A jump updates the stored location right away, so two quick Back presses don't both start from the same spot. Mouse buttons 3 and 4 also step it; trackpad swipes don't (WKWebView's swipe gesture is its own back/forward navigation).
- **Opening a document's own view.** On a fresh open (no `ViewState`, and the path isn't in recent files yet, so only the first time a file is opened) `DocumentTab` reads `getOpenAction` (a `Map` in pdf.js 6), `getPageMode`, and `getPageLayout`. `documentView` in `src/lib/viewModes.ts` maps them: `UseOutlines`/`UseThumbs` open the sidebar on Outline/Pages, and `SinglePage`, `OneColumn`, `TwoColumnLeft/Right`, `TwoPageLeft/Right` become scroll and spread modes. The open action's destination is scrolled to without recording a history stop. Restores always keep the saved view.
- **Page labels.** `getPageLabels()` is loaded on every document load and handed to `viewer.setPageLabels` once pages exist; labels that are just "1", "2", … are treated as none. The page box shows the label with "(n of N)", and `pageFromInput` takes an exact label, then a case-insensitive one, then a number.
- **Hand tool and Space.** `src/lib/handTool.ts` pans the container from a capture-phase `pointerdown`, so it also works over the editor layers without switching pdf.js's editor mode. Tools > Hand sets the editor mode to none and turns it on; holding Space turns it on until release from any tool (`holdHand`), except in text fields, form fields, free text editors, and buttons (`wantsSpace`). A tap of Space without a drag scrolls a screen (Shift goes back), since the keydown is prevented.
- **Editor options.** pdf.js applies `switchannotationeditorparams` to the selected editors when there are any, otherwise to the class defaults, which are static and shared by every viewer in the window. The toolbar shows the selected editor's values (from `annotationeditorparamschanged`) or the remembered ones (`clumsy.editorParams`), and only remembers changes made with nothing selected. Remembered values are pushed whenever an editor mode turns on with nothing selected; pdf.js fires the mode event after it selects a double-clicked editor, which is why the push checks the selection. `HIGHLIGHT_FREE` isn't settable: pdf.js draws a freehand highlight whenever a highlight drag starts off text, so only its thickness is offered.
- **Find.** `PatternFindController` runs regular expressions against pdf.js's page text, which is NFD-normalized. Unless Match Diacritics is on, combining marks (except the ones pdf.js keeps, such as viramas) are stripped from both the pattern and the page text, matched, and mapped back so a match covers its accents. With it on, the pattern is NFD-normalized and matches that would end before a mark are dropped.
- **Caret browsing.** WebKit draws no caret in non-editable text, so `src/lib/caretBrowsing.ts` draws one (`.caret-mark`) at the selection's focus and handles the keys itself: Left/Right through `Selection.modify` (⌥ by word), Up/Down by finding the nearest text-layer box on the next line (`nextLine` in `src/lib/caretLines.ts`, continuing to the next page) and the character offset under the caret's x, Home/End to the ends of the line's boxes. Shift extends. Keys inside the annotation and editor layers (a selected drawing being nudged) are left to pdf.js. It's on per window (`clumsy.caretBrowsing`) and only in the focused pane's active tab, so turning it on doesn't move a selection in another pane.
- **Commands, shortcuts, and menus.** `src/lib/commands.ts` is the single source of truth: every command's id, label, menu, and key combos. The same table builds the native menu bar (`src/lib/menu.ts`, via Tauri's JS menu API, so the menu shows each shortcut), resolves keyboard shortcuts in `App.tsx`, renders the Keyboard Shortcuts window (⌘K or ⌘/), and fills the Command Palette (⇧⌘P). Every path ends in `runCommand(id)` in `App.tsx`. The layout follows VS Code's defaults where a PDF viewer has an equivalent (⌘B sidebar, ⇧⌘E thumbnails, ⇧⌘O outline, ⌘N new tab, ⇧⌘N new window, ⌘P Go to File, ⌃G Go to Page, ⌘↑/⌘↓ first/last page, ⇧⌘T reopen closed tab, ⌥⌘S Save All); keep it that way when adding commands. `⌘1`–`⌘8` stay as Show Tab N, not focus pane. Go Back/Forward use VS Code's macOS keys (⌃- / ⌃⇧-); `ctrl` combos only exist on macOS, so other platforms will need their own (VS Code uses Alt+←/→). Function keys (F7) are menu accelerators even without a modifier, since they never type text. To add a command: add it to the table, place it in `menuLayout` if it belongs in a menu (the tests check every menu command is placed exactly once and no combo is used twice), and handle it in `runCommand`. Combos use physical keys (`event.code`), so ⌥ shortcuts work even though Option changes the typed character. Plain-letter combos (`h`, `n`, `Home`) are ignored while typing and never become menu accelerators, because a native accelerator swallows the key everywhere, including text fields. Combos that move the caret (`movesCaret`: arrows, Home, End with no modifier, ⌘, or ⌥, plus ⇧) are also ignored by the keydown router while typing; ⌘↑/⌘↓ are still menu accelerators, so when one comes from the native menu (`runCommand(id, true)`) while a field with a caret has focus (`hasCaret`), it moves that caret to the start or end (`moveCaretToEdge`) instead of changing pages. A click on the menu item does the same, since Tauri can't tell it from the accelerator; the palette always changes pages. The keydown router skips Escape inside an open `<dialog>` and ignores IME composition keys. Commands that only work with a split set `needsSplit` (disabled in the menu, hidden from the palette). Scroll and spread modes are check items driven by `checkedCommands` in `menu.ts`, one checked per group like a radio. Native check items toggle themselves on click, so clicking the already-checked mode would uncheck it with no state change to redraw it; their action re-checks the clicked item. Typing `:` and a page number or label in the Command Palette or Go to File offers a single "Go to page" item (`pageJumpItem`). The Command Palette lists every menu command available right now; Go to File (⌘P) lists this window's open tabs and then recent files. Both are one in-window modal `<dialog>` (`QuickPick`) with a fuzzy matcher (`src/lib/fuzzy.ts`). Closing it blurs its input before running the picked command: WebKit leaves focus on an input inside a closed `<dialog>`, which made palette Undo/Redo act on the search field. Closing a tab that has a path remembers it and its view (page, zoom, scroll) for Reopen Closed Tab, per window, up to 20. Native menu accelerators win over the webview's keydown, which is why Undo/Redo are custom items that route to the focused text field or to pdf.js's `editingaction` event; the predefined Undo would never reach pdf.js. Document commands set `needsDocument` and are disabled in the menu when the active tab has no PDF. The Rust side no longer builds menus.
- **Windows and dialogs.** About and Keyboard Shortcuts are separate Tauri windows (labels `about` and `shortcuts`) that load the same bundle; `main.tsx` picks the view from `?window=` in the URL. `openAuxWindow` in `platform.ts` creates the window or focuses the existing one and sends it new params (for example which About tab to show) through an `aux-window-params` event. Close Tab and Close Window first close a focused auxiliary window, because the app menu's actions run in the last focused document window. Closing the last document window closes the auxiliary ones. New windows are placed with `placeOverWindow` (`src/lib/windowPlacement.ts`): centered over the main window and clamped to the work area of the display it's on. Don't use Tauri's `center`, which always picks the primary display. Window and monitor positions come back in physical pixels; divide by each one's scale factor before mixing them. New window labels must be added to `capabilities/default.json`. Questions with only buttons use native alerts (`@tauri-apps/plugin-dialog`, see `src/lib/defaultAppPrompt.ts`). The password and signature prompts need inputs, so they stay as in-window `<dialog>`s styled as sheets (`.dialog.sheet`).
- **Title bar.** The window uses `titleBarStyle: Overlay` with `hiddenTitle`; the toolbar pads left for the traffic lights (except in fullscreen) and toolbar groups carry `data-tauri-drag-region`.
- **Third-party licenses.** `pnpm build` (and so every release) runs `scripts/third-party-licenses.mjs`, which collects license texts for the npm packages the UI bundles (production `dependencies`, walked transitively) and the Rust crates compiled into the binary (`cargo metadata`, normal dependencies only). For "A OR B" licenses it uses MIT when offered. Crates that ship without a license file get the shared Apache/MPL text or an MIT/BSD template with the crate's authors. Identical texts are listed once. The About window shows the result under Licenses. New dependencies are picked up automatically; check the "without a bundled license file" section of the output if a new license type appears.
- **Version** shown in the app comes from `tauri.conf.json` at build time (`__APP_VERSION__` in `vite.config.ts`). CI runs `scripts/set-version.mjs` so `package.json`, `tauri.conf.json`, and `Cargo.toml`/`Cargo.lock` all match the release, then commits them with the stamped changelog.

## Releases

Every push to `main` builds, signs, notarizes, and publishes a GitHub release (`.github/workflows/release.yml`). Pull requests run `ci.yml` instead.

- **Versioning** (`scripts/next-version.sh`): bump the patch of the latest `vX.Y.Z` tag. To jump to a new minor or major, set `version` in `src-tauri/tauri.conf.json` (for example `0.3.0`); the next push releases exactly that and later pushes continue from it. Don't hand-edit `package.json` or `Cargo.toml` for releases — the workflow keeps them in sync.
- **Changelog**: add user-facing changes under `## [Unreleased]` in `CHANGELOG.md` (Keep a Changelog sections: Added / Changed / Fixed / Removed; `**bold**` renders in the app). On release, the workflow moves those entries under `## [x.y.z] - date`, builds with the stamped file so What's New is correct, uses that section as the release notes, then commits the changelog and version files back to `main` as `Release vx.y.z`. If `[Unreleased]` is empty, the notes list commit subjects instead, but the version files are still committed.
- **If you've edited `CHANGELOG.md` locally while a release ran**, the pull can silently merge your new entries into the just-stamped version section. Check that they're still under `[Unreleased]` after pulling.
- **After every release `origin/main` is one commit ahead** (the version + changelog commit). Run `git pull --rebase` before pushing again, or set `git config pull.rebase true`. Pushes made with the workflow's `GITHUB_TOKEN` don't trigger new workflow runs, so there's no release loop.
- Releases run one at a time (`concurrency: release`). Pushes touching only `README.md`, `AGENTS.md`, `CLAUDE.md`, or `docs/` don't release. The workflow can also be run manually from the Actions tab.
- Assets are `Clumsy.dmg` and `Clumsy.zip`: universal (Apple Silicon + Intel), Developer ID signed, notarized, and stapled.

## Conventions

- Never commit test documents. `public/` is copied into the app bundle, and `public/*.pdf` is git-ignored for that reason; keep sample PDFs outside the repo. Review `git status` for new files before every commit instead of blindly staging everything.

- Match the existing style: no code comments unless the logic truly needs one, self-explanatory names, small pure helpers in `src/lib` with vitest coverage.
- Keep source files under 500 lines. When one grows past that, split it along a real seam (a hook, a component, a pure helper in `src/lib`) rather than arbitrarily.
- Global form-control resets use `:where(:is(button, input, select):not(.pdfViewer *))` on purpose: zero specificity so component classes win, and pdf.js's own controls (whose layers set huge font sizes) are left alone.
- pdf.js 6 API notes: `PDFDocumentProxy.destroy()` is gone (use `loadingTask.destroy()`); `page.render({ canvas, viewport })`; editor modes are set with `viewer.annotationEditorMode = { mode }`; default colors go through the `switchannotationeditorparams` event.
- Typecheck, test, clippy, and Rust tests must pass; the release workflow runs all of them before building.
- Commit messages: short imperative subject describing the change.
