# Clumsy

A lightweight PDF viewer built on Tauri. Releases are macOS-only today; Windows and Linux are planned, so keep platform-specific code behind `platform.ts` / `cfg(target_os)` and wording platform-neutral. Tagline: "No tricks, no acrobatics." Avoid naming other companies' products (for example Adobe Acrobat) in the app, README, or store listings. Tauri 2 (Rust) shell, React 19 + TypeScript UI, pdf.js 6 for rendering and markup. Sponsored by Texas Beard Company, the same branding used in TheAnnex and DutiHEHE.

Repo: https://github.com/ry4nolson/clumsy (public, MIT License). The local folder is still named `pdf-viewer`. The license covers code only: the Clumsy name and icon and the Texas Beard Company name and logos are excluded (see README).

## Commands

```bash
pnpm install
pnpm tauri dev                 # run the desktop app with hot reload
pnpm dev                       # browser-only UI at http://localhost:1420 (no file paths, menus, or recents)
pnpm test                      # vitest (tests/*.test.ts)
pnpm exec tsc --noEmit         # typecheck
cargo clippy --manifest-path src-tauri/Cargo.toml -- -D warnings
cargo test --manifest-path src-tauri/Cargo.toml --lib
pnpm tauri build --bundles app # local release build -> src-tauri/target/release/bundle/macos/Clumsy.app
pnpm licenses                  # regenerate public/third-party-licenses.txt (also runs as part of pnpm build)
```

- Node 20.19+ is required by Vite 8 (Node 22 recommended). pnpm is pinned through `packageManager` in `package.json`.
- Universal builds (`--target universal-apple-darwin`) need rustup's toolchain with `x86_64-apple-darwin` installed. Homebrew's `cargo` can't cross-compile, so put `~/.cargo/bin` first in `PATH` for those builds.

`src/lib/platform.ts` is the only place that talks to Tauri. Everything there has a browser fallback, so `pnpm dev` works for UI work.

## Architecture notes

- **Tabs and panes.** `src/lib/workspace.ts` is the pure, tested model: a map of tabs plus an ordered list of panes (each with its tab order, active tab, and flex size) and the focused pane. Every open document mounts its own `DocumentTab` with its own pdf.js `PDFViewer`; never swap documents inside one viewer, because unsaved highlights and notes live in the viewer's editor layer. `PaneGrid` lays panes out as a CSS grid (row 1 tab strips, row 2 documents, 5px divider columns between panes) and renders every `DocumentTab` as a sibling in one keyed list, positioned by `gridColumn`. That is what lets a tab move between panes without remounting: only its column changes, so scroll, zoom, and unsaved markup survive. Inactive tabs stay laid out but hidden (`visibility: hidden` + `inert`); `display: none` would reset their scroll position. App keeps per-tab `TabSnapshot`s (page, zoom, tool, modified, find state); the focused pane's active tab drives the toolbar, menus, and window title. Tab dragging and divider resizing are pointer-event based in `PaneGrid` (HTML5 drag and drop is unreliable in Tauri webviews); the divider has a widened invisible grab area. At most `MAX_PANES` (4) panes.
- **Document windows.** Every document window (label `main` or `doc-*`) runs the full `App` with its own workspace; `src/lib/documentWindows.ts` opens them, finds the window under a drop point, and hands tabs over; `useTabTransfer` drives it from the app. A live pdf.js document can't move between webviews, so moving a tab calls `saveDocument()` (unsaved markup is baked in), stashes the bytes in Rust (`stash_transfer` / `take_transfer`, raw IPC, taken once), and the receiving window reopens them with the same page and zoom. A tab that arrives with unsaved changes keeps a `carriedChanges` flag so it still reads as edited until saved; undo history from before the move is lost. Each window builds its own app menu and calls `activate()` (`setAsAppMenu`) when it gains focus, because menu callbacks run in the window that built them. Don't give menu items fixed ids: Tauri routes menu clicks through one app-wide id → handler map, so a shared id sends every window's clicks to the newest window. Keyboard shortcuts hide the problem because the focused page handles them first. Rust tracks the last focused document window (`windows.rs`) and sends Finder-opened files there with `emit_to`, which is why `files-opened` is listened for per webview. Each window reports its open paths and unsaved document names to Rust (`report_documents`) whenever they change; opening a path another window already has focuses that window's tab instead (`document_window`, `show-document` event), so one file never has two writers in different windows. The default-app launch prompt only runs in `main`. Closing the last document window also closes About/Shortcuts. Capabilities list `doc-*`. Tab tear-off is detected in `PaneGrid` when a drag ends outside the window; drops onto another window merge into its focused pane.
- **Start tabs.** Opening a file from a Start tab replaces that tab, like a browser's new-tab page. Opening a path that's already open anywhere switches to its tab, except Split Right, which deliberately opens a second copy. Closing the last tab in a pane removes the pane; closing the last tab overall leaves a Start tab.
- **Saving.** `pdfDocument.saveDocument()` writes markup and form values as an incremental update over the original bytes held by the worker, so repeated saves don't duplicate annotations. The Rust `write_pdf` command takes raw bytes with the path in a percent-encoded `x-path` header and writes atomically (temp file + rename, into the symlink's real target, keeping the original permissions), `.pdf` paths only. Each tab keeps the file's stamp (mtime + size) from when it was read; saving to the same path sends it as `x-expected-stamp`, and if the file changed on disk Rust refuses with `changed-on-disk` so the app can ask before overwriting. Saving returns the new stamp.
- **External changes.** `useExternalChanges` polls `file_stamp` for each open file every 2 seconds while the window is visible, and right away when it gains focus. A tab reloads in place (same page, zoom, and scroll, via `viewState()`) only when `canReload` in `src/lib/externalChanges.ts` says so: the stamp changed, nothing is unsaved or carried over from another window, and the draw or text tool isn't active (those can hold edits pdf.js hasn't committed yet). Before swapping, the stamp must hold steady for 300 ms and the new bytes must end in `%%EOF`, so a file another program is still writing isn't loaded half-done. Edited tabs are left alone; Save's changed-on-disk prompt covers them.
- **Page edits.** `src/lib/pageEdits.ts` does the structural work with `@cantoo/pdf-lib` (the maintained pdf-lib fork, which can also encrypt): reorder, delete, rotate, insert another PDF, extract, combine. The low-level page tree work lives in `src/lib/pdfStructure.ts`. pdf.js can't change a document's pages, so every page edit takes the current bytes from `viewer.save()` (unsaved markup is baked in, like moving a tab between windows), rewrites them, and swaps them into the tab as a new `source` with `carriedChanges: true`, keeping zoom and moving to the right page (`pageAfterEdit`). Every edit first flattens the page tree into one `/Pages` node, copying inherited `Resources`/`MediaBox`/`CropBox`/`Rotate` onto each page, and then just rewrites `/Kids`; pdf-lib's own `removePage`/`insertPage` corrupt the tree when every page moves and let inserted pages inherit a branch's rotation. Removing pages (delete, and extract, which removes everything else) also removes their annotations and form widgets, fields left with no widgets (and their `/CO` calculation-order entries), tagged-PDF structure elements whose content was all on those pages (`src/lib/pdfStructTree.ts`, so their `/Alt` and `/ActualText` go too, along with their `/IDTree` entries), links, bookmarks, and an `/OpenAction` that pointed at them (named destinations are resolved through `/Dests` and the `/Names` tree before they're pruned, since LaTeX and many other producers only use names), and named destinations, then nulls any other reference to them. Removing pages also drops XFA form data (pdf.js doesn't render it, and it keeps its own copy of every field value); other edits keep it, because a dynamic XFA form has nothing else. Structure elements reached through two parents are decided once, and an `OBJR` pointing at an annotation is judged by that annotation, not by the element's `/Pg`. Pages copied in from another file lose `/StructParents` so they don't collide with the target's structure tree. Before saving, `collectGarbage` drops every object the trailer can't reach and pdf-lib rewrites the whole file, so a deleted page's content is really gone and no earlier revision survives. That matters: people delete pages to remove private information. Inserted and combined pages are copied by copying the source's (flattened) page tree in one pass, so links between them point at the copies. Their form fields stop being fields, and the first file's fields keep working when combining. Password-protected PDFs are refused with a clear message.
- **Page edit timing.** `usePageEdits` keeps per-tab state: a queue (edits run one at a time), the `pending` version (shown but not yet loaded by pdf.js; the next edit starts from it), a `generation` counter, and up to 20 earlier versions, capped at 256 MB in total (`trimHistory`). Commands capture the generation when issued and are dropped if another edit landed first, because their page indices refer to the old version. History belongs to one `source` object: if anything else replaces the tab's source (an outside change reloading the tab), the history is cleared, and an edit whose baseline changed while it was computing is cancelled. Save and moving a tab to another window first `await settled(tabId)`. Save only clears `carriedChanges` if the source it saved is still the tab's source. If pdf.js can't open an edited version, `documentFailed` restores the previous one instead of closing the tab. Undo and Redo are routed by `routeStep`: Undo goes to pdf.js while pdf.js has something to undo (`viewer.editHistory()`, from pdf.js's `editingstateschanged` event, so it survives Save), otherwise to page history, except after the user typed into a form field since this version loaded (`changed`, set by `input`/`change` events inside the annotation layer; typing isn't on pdf.js's undo stack, and page undo would take the typed values with it). Don't use `annotationStorage` modification for this: pdf.js writes to it while rendering radio buttons. Redo goes to pdf.js while pdf.js has something to redo; if markup or typing sits on top of the current version, page redo is cleared instead, because those versions predate it. While an edit is queued or a version is loading, Undo and Redo are queued behind it instead of going to pdf.js. `documentLoaded`/`documentFailed` get the `source` that finished loading and ignore stale ones, so a quick Undo can't clear the wait for a newer version. Selection lives in `DocumentTab` and only counts while it includes the current page (`followCurrentPage`), so scrolling away quietly drops it; commands act on the selection or else the current page. Dragging to the same spot is a no-op (`changesDocument`). Thumbnail drag-to-reorder is pointer based like tab dragging. Dropping PDFs on a visible sidebar inserts them at the drop line (`src/lib/dropTarget.ts`, marked with `data-drop-*` attributes React doesn't manage); dropping anywhere else opens them as before. The thumbnail context menu is a native popup (`showContextMenu`).
- **File access.** The webview can only read or write paths Rust handed out: files picked in Rust's dialogs (`pick_pdf`, `pick_pdfs`, `pick_image`, `pick_save_path`), dropped on a window, opened from Finder or the command line, or in recent files. `files.rs` keeps that allowlist (canonical paths) and `read_pdf` / `read_image` / `write_pdf` / `record_recent_file` check it, so a compromised page can't read arbitrary files. Don't call the dialog plugin's `open`/`save` from JS for files; add a Rust command that allows the result. File IPC commands are `async` so large reads and writes don't block the main thread (sync commands run on it). The CSP lives in `tauri.conf.json`; `devCsp` is `null`, so `pnpm tauri dev` doesn't enforce it. Check CSP changes with a `pnpm tauri build` app.
- **Quitting.** Quit is a custom command (⌘Q), not the predefined item, because the predefined one terminates without any chance to ask. It reports this window's documents (finishing in-progress edits first) and calls `request_quit`, which exits right away or shows one native "Discard and Quit" alert listing every unsaved document across windows. Quitting from the Dock or logging out still skips the prompt: tao doesn't implement `applicationShouldTerminate`.
- **Dark pages.** The default ("Keep images") applies `invert(0.92) hue-rotate(180deg)` to `.canvasWrapper` and the editor layer, then draws each image's original pixels into an unfiltered overlay canvas (`.image-restore`). Image rectangles come from pdf.js's image tracker (`imagesRightClickMinSize: 0`) and are rotated by `src/lib/imageRegions.ts`. pdf.js's own `pageColors` high-contrast mode recolors images too, so it isn't used. `enableDetailCanvas` is off because the detail canvas would cover the overlay.
- **Fit width / fit page on resize.** `usePdfViewer` re-applies preset zooms when the viewer's *border-box* size changes. Don't observe the content box: with always-visible scrollbars the scrollbar appearing narrows the content box, the page re-fits smaller, the scrollbar disappears, and the page loops forever (it shakes and pins a CPU). `.viewer-container` also uses `scrollbar-gutter: stable`.
- **Recent files.** Rust owns the list (`~/Library/Application Support/com.ry4nolson.clumsy/recent-files.json`, max 20, menu shows 10) so the native menu works before the webview loads. The frontend records a path after a successful load or a Save As, and listens for `recent-files-changed`.
- **Default PDF app.** `default_app.rs` calls `LSCopyDefaultRoleHandlerForContentType` / `LSSetDefaultRoleHandlerForContentType` for `com.adobe.pdf` (what `duti` uses). Only offered when running from an installed `.app`; dev builds aren't registered bundles.
- **Commands, shortcuts, and menus.** `src/lib/commands.ts` is the single source of truth: every command's id, label, menu, and key combos. The same table builds the native menu bar (`src/lib/menu.ts`, via Tauri's JS menu API, so the menu shows each shortcut), resolves keyboard shortcuts in `App.tsx`, renders the Keyboard Shortcuts window (⌘K or ⌘/), and fills the Command Palette (⇧⌘P). Every path ends in `runCommand(id)` in `App.tsx`. The layout follows VS Code's defaults where a PDF viewer has an equivalent (⌘B sidebar, ⇧⌘E thumbnails, ⇧⌘O outline, ⌘N new tab, ⇧⌘N new window, ⌘P Go to File, ⌃G Go to Page, ⌘↑/⌘↓ first/last page, ⇧⌘T reopen closed tab, ⌥⌘S Save All); keep it that way when adding commands. `⌘1`–`⌘8` stay as Show Tab N, not focus pane. To add a command: add it to the table, place it in `menuLayout` if it belongs in a menu (the tests check every menu command is placed exactly once and no combo is used twice), and handle it in `runCommand`. Combos use physical keys (`event.code`), so ⌥ shortcuts work even though Option changes the typed character. Plain-letter combos (`h`, `n`, `Home`) are ignored while typing and never become menu accelerators, because a native accelerator swallows the key everywhere, including text fields. Combos that move the caret (`movesCaret`: arrows, Home, End with no modifier, ⌘, or ⌥, plus ⇧) are also ignored by the keydown router while typing; ⌘↑/⌘↓ are still menu accelerators, so when one comes from the native menu (`runCommand(id, true)`) while a field with a caret has focus (`hasCaret`), it moves that caret to the start or end (`moveCaretToEdge`) instead of changing pages. A click on the menu item does the same, since Tauri can't tell it from the accelerator; the palette always changes pages. The keydown router skips Escape inside an open `<dialog>` and ignores IME composition keys. Commands that only work with a split set `needsSplit` (disabled in the menu, hidden from the palette). The Command Palette lists every menu command available right now; Go to File (⌘P) lists this window's open tabs and then recent files. Both are one in-window modal `<dialog>` (`QuickPick`) with a fuzzy matcher (`src/lib/fuzzy.ts`). Closing a tab that has a path remembers it and its view (page, zoom, scroll) for Reopen Closed Tab, per window, up to 20. Native menu accelerators win over the webview's keydown, which is why Undo/Redo are custom items that route to the focused text field or to pdf.js's `editingaction` event; the predefined Undo would never reach pdf.js. Document commands set `needsDocument` and are disabled in the menu when the active tab has no PDF. The Rust side no longer builds menus.
- **Windows and dialogs.** About and Keyboard Shortcuts are separate Tauri windows (labels `about` and `shortcuts`) that load the same bundle; `main.tsx` picks the view from `?window=` in the URL. `openAuxWindow` in `platform.ts` creates the window or focuses the existing one and sends it new params (for example which About tab to show) through an `aux-window-params` event. Close Tab and Close Window first close a focused auxiliary window, because the app menu's actions run in the last focused document window. Closing the last document window closes the auxiliary ones. New windows are placed with `placeOverWindow` (`src/lib/windowPlacement.ts`): centered over the main window and clamped to the work area of the display it's on. Don't use Tauri's `center`, which always picks the primary display. Window and monitor positions come back in physical pixels; divide by each one's scale factor before mixing them. New window labels must be added to `capabilities/default.json`. Questions with only buttons use native alerts (`@tauri-apps/plugin-dialog`, see `src/lib/defaultAppPrompt.ts`). The password and signature prompts need inputs, so they stay as in-window `<dialog>`s styled as sheets (`.dialog.sheet`).
- **Title bar.** The window uses `titleBarStyle: Overlay` with `hiddenTitle`; the toolbar pads left for the traffic lights (except in fullscreen) and toolbar groups carry `data-tauri-drag-region`.
- **Third-party licenses.** `pnpm build` (and so every release) runs `scripts/third-party-licenses.mjs`, which collects license texts for the npm packages the UI bundles (production `dependencies`, walked transitively) and the Rust crates compiled into the binary (`cargo metadata`, normal dependencies only). For "A OR B" licenses it uses MIT when offered. Crates that ship without a license file get the shared Apache/MPL text or an MIT/BSD template with the crate's authors. Identical texts are listed once. The About window shows the result under Licenses. New dependencies are picked up automatically; check the "without a bundled license file" section of the output if a new license type appears.
- **Version** shown in the app comes from `tauri.conf.json` at build time (`__APP_VERSION__` in `vite.config.ts`); CI sets it from the computed release version.

## Releases

Every push to `main` builds, signs, notarizes, and publishes a GitHub release (`.github/workflows/release.yml`). Pull requests run `ci.yml` instead.

- **Versioning** (`scripts/next-version.sh`): bump the patch of the latest `vX.Y.Z` tag. To jump to a new minor or major, set `version` in `src-tauri/tauri.conf.json` (for example `0.2.0`); the next push releases exactly that and later pushes continue from it.
- **Changelog**: add user-facing changes under `## [Unreleased]` in `CHANGELOG.md` (Keep a Changelog sections: Added / Changed / Fixed / Removed; `**bold**` renders in the app). On release, the workflow moves those entries under `## [x.y.z] - date`, builds with the stamped file so What's New is correct, uses that section as the release notes, then commits it back to `main` as `Release vx.y.z`. If `[Unreleased]` is empty, nothing is stamped and the notes list commit subjects instead.
- **If you've edited `CHANGELOG.md` locally while a release ran**, the pull can silently merge your new entries into the just-stamped version section. Check that they're still under `[Unreleased]` after pulling.
- **After every release `origin/main` is one commit ahead** (the changelog commit). Run `git pull --rebase` before pushing again, or set `git config pull.rebase true`. Pushes made with the workflow's `GITHUB_TOKEN` don't trigger new workflow runs, so there's no release loop.
- Releases run one at a time (`concurrency: release`). Pushes touching only `README.md`, `AGENTS.md`, `CLAUDE.md`, or `docs/` don't release. The workflow can also be run manually from the Actions tab.
- Assets are `Clumsy.dmg` and `Clumsy.zip`: universal (Apple Silicon + Intel), Developer ID signed, notarized, and stapled.

The source is `src-tauri/icons/app-icon.svg` (1024×1024, macOS icon grid: 824px rounded square at 100,100, radius ≈185). Regenerate every size with:

```bash
pnpm tauri icon src-tauri/icons/app-icon.svg
rm -r src-tauri/icons/android src-tauri/icons/ios   # desktop-only app
```

Check legibility at 32px before committing. Keep icon sources out of `public/`, which ships inside the app.

## Conventions

- Never commit test documents. `public/` is copied into the app bundle, and `public/*.pdf` is git-ignored for that reason; keep sample PDFs outside the repo. Review `git status` for new files before every commit instead of blindly staging everything.

- Match the existing style: no code comments unless the logic truly needs one, self-explanatory names, small pure helpers in `src/lib` with vitest coverage.
- Keep source files under 500 lines. When one grows past that, split it along a real seam (a hook, a component, a pure helper in `src/lib`) rather than arbitrarily.
- Global form-control resets use `:where(:is(button, input, select):not(.pdfViewer *))` on purpose: zero specificity so component classes win, and pdf.js's own controls (whose layers set huge font sizes) are left alone.
- pdf.js 6 API notes: `PDFDocumentProxy.destroy()` is gone (use `loadingTask.destroy()`); `page.render({ canvas, viewport })`; editor modes are set with `viewer.annotationEditorMode = { mode }`; default colors go through the `switchannotationeditorparams` event.
- Typecheck, test, clippy, and Rust tests must pass; the release workflow runs all of them before building.
- Commit messages: short imperative subject describing the change.
