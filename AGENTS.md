# Clumsy

A lightweight PDF viewer built on Tauri that also opens Markdown files. Releases are macOS-only today; Windows and Linux are planned, so keep platform-specific code behind `platform.ts` / `cfg(target_os)` and wording platform-neutral. Tagline: "No tricks, no acrobatics." Avoid naming other companies' products (for example Adobe Acrobat) in the app, README, or store listings. Tauri 2 (Rust) shell, React 19 + TypeScript UI, pdf.js 6 for rendering and markup, markdown-it and CodeMirror 6 for Markdown. Sponsored by Texas Beard Company, the same branding used in TheAnnex and DutiHEHE.

Repo: https://github.com/ry4nolson/clumsy (public, MIT License). The local folder is still named `pdf-viewer`. The license covers code only: the Clumsy name and icon and the Texas Beard Company name and logos are excluded (see README).

## Commands

```bash
pnpm install
pnpm tauri dev                 # run the desktop app with hot reload
pnpm dev                       # browser-only UI at http://localhost:1420 (no file paths, menus, or recents)
pnpm test                      # vitest (tests/*.test.ts)
pnpm exec tsc --noEmit         # typecheck
cargo clippy --manifest-path src-tauri/Cargo.toml -- -D warnings
cargo test --manifest-path src-tauri/Cargo.toml --lib
pnpm tauri build --bundles app # local release build -> src-tauri/target/release/bundle/macos/Clumsy.app
pnpm licenses                  # regenerate public/third-party-licenses.txt (also runs as part of pnpm build)
```

- Node 20.19+ is required by Vite 8 (Node 22 recommended). pnpm is pinned through `packageManager` in `package.json`.
- Universal builds (`--target universal-apple-darwin`) need rustup's toolchain with `x86_64-apple-darwin` installed. Homebrew's `cargo` can't cross-compile, so put `~/.cargo/bin` first in `PATH` for those builds.

## Architecture notes

- **Tabs and panes.** `src/lib/workspace.ts` is the pure, tested model: a map of tabs plus an ordered list of panes (each with its tab order, active tab, and flex size) and the focused pane. Every open document mounts its own `DocumentTab` with its own pdf.js `PDFViewer`; never swap documents inside one viewer, because unsaved highlights and notes live in the viewer's editor layer. `PaneGrid` lays panes out as a CSS grid (row 1 tab strips, row 2 documents, 5px divider columns between panes) and renders every `DocumentTab` as a sibling in one keyed list, positioned by `gridColumn`. That is what lets a tab move between panes without remounting: only its column changes, so scroll, zoom, and unsaved markup survive. Inactive tabs stay laid out but hidden (`visibility: hidden` + `inert`); `display: none` would reset their scroll position. App keeps per-tab `TabSnapshot`s (page, zoom, tool, modified, find state); the focused pane's active tab drives the toolbar, menus, and window title. Tab dragging and divider resizing are pointer-event based in `PaneGrid` (HTML5 drag and drop is unreliable in Tauri webviews); the divider has a widened invisible grab area. At most `MAX_PANES` (4) panes.
- **Document windows.** Every document window (label `main` or `doc-*`) runs the full `App` with its own workspace; `src/lib/documentWindows.ts` opens them, finds the window under a drop point, and hands tabs over; `useTabTransfer` drives it from the app. A live pdf.js document can't move between webviews, so moving a tab calls `saveDocument()` (unsaved markup is baked in), stashes the bytes in Rust (`stash_transfer` / `take_transfer`, raw IPC, taken once), and the receiving window reopens them with the same page and zoom. A tab that arrives with unsaved changes keeps a `carriedChanges` flag so it still reads as edited until saved; undo history from before the move is lost. Each window builds its own app menu and calls `activate()` (`setAsAppMenu`) when it gains focus, because menu callbacks run in the window that built them. Don't give menu items fixed ids: Tauri routes menu clicks through one app-wide id → handler map, so a shared id sends every window's clicks to the newest window. Keyboard shortcuts hide the problem because the focused page handles them first. Rust tracks the last focused document window (`windows.rs`) and sends Finder-opened files there with `emit_to`, which is why `files-opened` is listened for per webview. Each window reports its open paths and unsaved document names to Rust (`report_documents`) whenever they change; opening a path another window already has focuses that window's tab instead (`document_window`, `show-document` event), so one file never has two writers in different windows. The default-app launch prompt only runs in `main`. Capabilities list `doc-*`. Tab tear-off is detected in `PaneGrid` when a drag ends outside the window; drops onto another window merge into its focused pane.
- **Start tabs.** Opening a file from a Start tab replaces that tab, like a browser's new-tab page. Opening a path that's already open anywhere switches to its tab, except Split Right, which deliberately opens a second copy. Closing the last tab in a pane removes the pane; closing the last tab overall leaves a Start tab.
- **Saving.** `pdfDocument.saveDocument()` writes markup and form values as an incremental update over the original bytes held by the worker, so repeated saves don't duplicate annotations. The Rust `write_pdf` command takes raw bytes with the path in a percent-encoded `x-path` header and writes atomically (temp file + rename, into the symlink's real target, keeping the original permissions), `.pdf` paths only. Each tab keeps the file's stamp (mtime + size) from when it was read; saving to the same path sends it as `x-expected-stamp`, and if the file changed on disk Rust refuses with `changed-on-disk` so the app can ask before overwriting. Saving returns the new stamp. Markdown tabs save their text through `write_markdown` (`.md`/`.markdown` only) with the same atomic write and stamp check. A path Rust only allowed for reading (a file opened from a Markdown link) answers `not-writable`, and Save falls back to a Save As dialog (`writeTo` in `useSaveDocument.ts`).
- **External changes.** `useExternalChanges` polls `file_stamp` for each open file every 2 seconds while the window is visible, and right away when it gains focus. A tab reloads in place (same page, zoom, and scroll, via `viewState()`) only when `canReload` in `src/lib/externalChanges.ts` says so: the stamp changed, nothing is unsaved or carried over from another window, and the draw or text tool isn't active (those can hold edits pdf.js hasn't committed yet). Before swapping, the stamp must hold steady for 300 ms and a PDF's new bytes must end in `%%EOF`, so a file another program is still writing isn't loaded half-done. A Markdown tab has no tools, so it reloads whenever its text matches what was last saved and nothing was carried over; its new bytes only have to decode as UTF-8, and the view comes back on the same source line. Edited tabs are left alone; Save's changed-on-disk prompt covers them.
- **Page edits.** `src/lib/pageEdits.ts` does the structural work with `@cantoo/pdf-lib` (the maintained pdf-lib fork, which can also encrypt): reorder, delete, rotate, insert another PDF, extract, combine. The low-level page tree work lives in `src/lib/pdfStructure.ts`. pdf.js can't change a document's pages, so every page edit takes the current bytes from `viewer.save()` (unsaved markup is baked in, like moving a tab between windows), rewrites them, and swaps them into the tab as a new `source` with `carriedChanges: true`, keeping zoom and moving to the right page (`pageAfterEdit`). Every edit first flattens the page tree into one `/Pages` node, copying inherited `Resources`/`MediaBox`/`CropBox`/`Rotate` onto each page, and then just rewrites `/Kids`; pdf-lib's own `removePage`/`insertPage` corrupt the tree when every page moves and let inserted pages inherit a branch's rotation. Removing pages (delete, and extract, which removes everything else) also removes their annotations and form widgets, fields left with no widgets (and their `/CO` calculation-order entries), tagged-PDF structure elements whose content was all on those pages (`src/lib/pdfStructTree.ts`, so their `/Alt` and `/ActualText` go too, along with their `/IDTree` entries), links, bookmarks, and an `/OpenAction` that pointed at them (named destinations are resolved through `/Dests` and the `/Names` tree before they're pruned, since LaTeX and many other producers only use names), and named destinations, then nulls any other reference to them. Removing pages also drops XFA form data (pdf.js doesn't render it, and it keeps its own copy of every field value); other edits keep it, because a dynamic XFA form has nothing else. Structure elements reached through two parents are decided once, and an `OBJR` pointing at an annotation is judged by that annotation, not by the element's `/Pg`. Pages copied in from another file lose `/StructParents` so they don't collide with the target's structure tree. Before saving, `collectGarbage` drops every object the trailer can't reach and pdf-lib rewrites the whole file, so a deleted page's content is really gone and no earlier revision survives. That matters: people delete pages to remove private information. Inserted and combined pages are copied by copying the source's (flattened) page tree in one pass, so links between them point at the copies. Their form fields stop being fields, and the first file's fields keep working when combining. Password-protected PDFs are refused with a clear message. Page labels follow their pages: every edit except rotation reads the `/PageLabels` number tree (`src/lib/pdfPageLabels.ts`), maps each label to its page ref, and writes a fresh tree with `encodePageLabels` (`src/lib/pageLabels.ts`) that finds decimal, roman, and letter runs and falls back to a prefix-only range per page. Inserted and combined pages bring their own file's labels, or their new page number when that file has none. A file without labels never gains them from these edits. Pages > Page Labels… edits them directly: `PageLabelsDialog` (an in-window sheet rendered by `DocumentTab`, opened through `DocumentHandle.editPageLabels`) sends a `label` page action, and the `label` page edit rewrites the tree from `relabelRange`, so it's queued, undoable, and marks the tab edited like the others. The sheet starts on the current page's run (`numberingAt`, `runEnd`) or the selected pages, so its prefilled values change nothing until edited; ranges that leave every page with its own number delete `/PageLabels`.
- **Comparing documents.** A comparison is two tab ids held by `useComparison`; `workspace.ts` knows nothing about it. It ends when either tab closes, leaves the window, or both land in the same pane. `pdfText.ts` reads each page's `getTextContent()` (cached per `PDFDocumentProxy`) and `diffTokens.ts` turns the items into words with boxes in page fractions at the page's own rotation (`getViewport({ scale: 1 })` applies `/Rotate`, so drawing only adds `viewer.pagesRotation`). Items that continue a word are joined, line-end hyphens are joined, soft hyphens dropped, text NFKC-normalized, and content order is kept (no reading-order sort, which would interleave columns). The worker diffs the whole token stream with `diff` (jsdiff's `diffArrays`, 4 s timeout) and falls back to page-by-page (300 ms each, then the whole page counts as changed). `buildComparison` slides pure insertions/removals to start on a line (`slideToLineStarts`), merges word boxes per line, places a thin marker where text is missing on the other side, notes pages that are wholly added/removed or have no text, and records one anchor per matched line for linked scrolling (`syncLocation`). Highlights are DOM in a `.diff-layer` on each page div, never annotations, so nothing reaches Save. pdf.js's `reset()` removes unknown children on zoom and rotation, so the layer is re-attached on `scalechanging`, `rotationchanging`, and `pagerendered`. Linked scrolling remembers the `scrollTop` it set on the follower and ignores that one echo. Recomputes when either tab's `source` changes (page edits, outside reloads, Swap); markup and form typing don't change the text. Each change keeps an 80-character `before`/`after` snippet for the sidebar plus the full `beforeText`/`afterText` and word counts per side. Export Comparison Report (`exportComparison`) lays out a PDF from those in `src/lib/comparisonReport.ts` with `@cantoo/pdf-lib` and its standard Helvetica (WinAnsi only: other characters are NFKD-stripped of accents or drawn as `?`, so no font is fetched or bundled), then saves it through `pick_save_path` + `write_pdf`.
- **Document Map.** `DocumentMap` is a flex sibling of `.viewer-area` in each `DocumentTab` (a pane, not an overlay), on by default and toggled with ⌥⌘B (`clumsy.documentMap`). Its layout comes from the viewer's own page divs (`getBoundingClientRect`, re-measured by a `ResizeObserver` on `.pdfViewer`), normalized by the widest page so zoom doesn't change the map. `layoutMap` in `src/lib/documentMap.ts` fits every page into the pane's height, down to `MIN_PAGE_WIDTH`, then lets the map overflow. The pane's width follows the scaled pages (`layout.width`, at most `MAP_MAX_WIDTH`), so it narrows for long documents; the viewer's fit-width re-fit this causes doesn't feed back, because the layout only depends on the pages' proportions. Viewer and map positions are converted piecewise-linearly between page and gap stops (`toMap`), since the viewer's gaps are fixed pixels at any zoom. When the map overflows, the slider moves linearly with the viewer's scroll ratio and the map content is offset from that, like VS Code; a linear content offset instead makes the slider stall inside pages and jump at gaps. Dragging inverts this with a binary search (`scrollForSlider`). Pages render once at the pane's full width (a one-at-a-time queue per document) and stay rendered after first being near view; rotation re-renders them. Find marks come from pdf.js's `pageMatches`, which index into the concatenated `item.str`s of `getTextContent({ disableNormalization: true })` with no characters for line ends (that's how pdf.js's own highlighter reads them; `rangeRects` in `diffTokens.ts`), and only show while the find controller's `highlightMatches` is on: pdf.js re-sends the full match count after the find bar closes.
- **Markdown tabs.** `.md`/`.markdown` files open as their own tab kind (`kind: "markdown"`, `MarkdownDocTab` in `src/lib/tabs.ts`), not as a flavor of `"document"`: `kind === "document"` still means "has a pdf.js viewer", so page edits, comparison, image export, and the PDF handle map leave Markdown alone. `isFileTab` covers both where a path or name is all that matters (title, quit, Save All, Reveal in Finder, recent files, dedupe by path). `useWorkspace` keeps separate `markdownHandles` and `markdownSnapshots`; `openSource` takes either source (`isMarkdownSource`). Reading goes through `readDocumentFromPath`, which picks by extension. Text is strict UTF-8 (`decodeText` refuses anything else rather than corrupt it on save) with the BOM and CRLF/LF remembered in `TextFormat` and written back by `encodeText`; Rust `read_markdown`/`write_markdown` are gated by `is_markdown` and use the same atomic write and changed-on-disk stamp as PDFs. The rendered view is markdown-it (`src/lib/markdown.ts`: GFM tables, linkify, task lists, footnotes, front matter as a YAML block, highlight.js common languages without auto-detect) sanitized by DOMPurify (`markdownDom.ts`: no `<style>`, forms, frames, or `target`) and set as `innerHTML` by hand, so find marks and resolved images can be added without React touching them. A core rule stamps every block token with `data-line`/`data-line-end` from its source map and gives headings GitHub-style unique ids. Local images move to `data-local-src` during sanitizing and load through `read_linked_image` as blob URLs (cached per tab, revoked on unmount); `read_linked_image` and `open_linked_file` only resolve relative to an open Markdown file and only return images or `.md`/`.pdf` files. `open_linked_file` puts its result in `LinkedPaths`, a read-only allowlist: reads and stamps accept it, writes answer `not-writable` and Save falls back to Save As, and it never reaches recent files, so a page that calls the command directly can't overwrite a file the user never picked. Remote `https:` images load (`img-src https:` in the CSP). Every link click is handled: `#id` scrolls, http(s)/mailto go to the browser, `.md`/`.pdf` paths open in a tab, anything else is dropped. The sanitizer also removes `<map>`/`<area>` and SVG link targets, and a `navigation-guard` plugin in `lib.rs` (`is_app_url`) refuses any webview navigation off the app's own origin, so a stray link can't replace a window and its unsaved tabs. ⇧⌘V (`toggleMarkdownSource`, VS Code's Open Preview key) switches to a CodeMirror 6 editor (`markdownEditor.ts`), dynamically imported the first time so rendered-only use doesn't load it, then kept mounted and hidden like inactive tabs so its undo history survives. Position is always a fractional source line: in the rendered view `lineAtOffset`/`offsetForLine` (`markdownScroll.ts`) interpolate inside the innermost `[data-line]` block at the top of the viewport (and between blocks across gaps); in the editor `lineBlockAtHeight`/`lineBlockAt` do the same. Anchoring the top line rather than the middle keeps images and font changes from drifting it. After a programmatic scroll the line is held and re-applied by a `ResizeObserver` while images load, until the user scrolls. That same line is the `MarkdownViewState` (`mode`, `line`, `zoom`) used by outside-change reloads, Reopen Closed Tab, Split Right, and moving a tab between windows (`TabTransfer.format: "markdown"`, UTF-8 bytes through the same stash). Edits re-render the preview only when switching back. Find reuses `compileFindPattern`/`findPatternMatches` over NFD text mapped back to the original (`textFind.ts`), wrapping `<mark>`s in the rendered DOM (`domFind.ts`, rebuilt per query) or CodeMirror decorations in source. Commands that also make sense for Markdown carry `markdown: true` (save, find, sidebar, outline, zoom, first/last page as top/bottom); `needsMarkdown` commands only work there; `documentAvailable` applies both to the menu, the palette, and `runCommand`, and `useMarkdownCommands` handles them before the PDF routers. Native Undo/Redo reach CodeMirror only through `editingCommand`, since the menu accelerator swallows ⌘Z before the editor's keymap sees it; in source mode they go to the editor's history unless another text field (the find bar) has focus, so the Command Palette's Undo works too. The minimap (`MarkdownMap`, shown with the same `clumsy.documentMap` toggle and ⌥⌘B as the PDF Document Map) is a clone of the rendered `<article>` scaled to `MAP_MAX_WIDTH`, re-cloned (debounced) whenever the article mutates or resizes, so loaded images and find marks show up in it. Its slider reuses `sliderFor`/`scrollForSlider` with a one-block layout (`documentLayout` in `src/lib/markdownMap.ts`). In source mode there's no rendered scroll position, so the editor's visible line range is mapped onto the rendered layout with `offsetForLine` (`sourceViewport`) and map clicks and drags scroll the editor to `lineAtOffset` of the target, the same line mapping the ⇧⌘V toggle uses. Live reload uses the same polling as PDFs; a Markdown tab reloads when its text matches the last saved text and it has no carried changes.
- **Pages as images.** Export Pages as Images (File menu) and Export Selected Pages as Images (Pages menu, thumbnail context menu) are the same command: the sheet offers all pages, the current page, the selection (`explicitPages`, same `followCurrentPage` rule as other page commands; shown only when there is one and picked by default), or a typed range like "1-3, 5, 8-" (`parsePageRange` in `src/lib/pageRanges.ts`; an empty or invalid range disables Export). Resolution is 72, 150, or 300 dpi, with the current page's pixel size shown (`exportPixelSize`). The last format, resolution, and JPEG quality are kept in `clumsy.exportImages`; the page choice isn't. Pages render from the tab's loaded pdf.js document, not from saved bytes: pdf.js's print path (`intent: "print"`, `AnnotationMode.ENABLE_STORAGE`, `printAnnotationStorage: annotationStorage.print`) draws unsaved markup and typed form values the way they'd print, after `commitEdits()` and `settled(tabId)`. The storage snapshot is taken once, so edits made while an export runs aren't in it. Each page renders into its own detached canvas, one at a time, then the canvas is zeroed and `page.cleanup()` frees that page's operator lists and images (this also drops the on-screen page's cached operator list; pdf.js refetches it on the next render). Output honors the page's saved `/Rotate` (`getViewport` applies it) but not the view-only rotation (⌘R), which isn't part of the document. Scale is dpi/72, capped at 2^25 pixels and 16384 px per side (`renderScale`) so huge pages don't fail to allocate. One page goes through a save dialog as "<doc> - page 3.png"; several go into a picked folder as "<doc> - page 01.png", zero-padded to the document's page count. If any of those names already exist, Clumsy asks once ("Replace" or "Cancel") before writing anything; without that answer Rust opens files with `create_new`, so nothing is ever replaced silently, even if a file appears mid-export. Cancelling stops after the current page and keeps the files already written. When at least one file was written (including a cancelled export), a native alert offers Show in Finder, which reveals the first file; `write_image` returns the path it wrote for this.
- **PDFs from images.** New PDF from Images (File menu), dropping images on the window, and Insert Pages from File (which now picks PDFs and images, several at once) all go through `src/lib/imagePdf.ts`. Dropping or picking a mix keeps the order: consecutive images become one PDF (`groupRuns`), PDFs stay as they are, and the pieces are combined. Away from the thumbnails, dropped PDFs open as before and all the dropped images become one new unsaved tab (`carriedChanges`), named after the first image ("IMG_0001 and 3 more.pdf"). Inserting goes through `usePageEdits` (`insertFiles` → `performEdit`), so undo, redo, and the generation rules are unchanged. One page per image; the page is the image at 72 pt per inch (one pixel to a point), shrunk to fit Letter in the image's own orientation and never enlarged (`imagePageSize`). JPEGs are embedded byte for byte and never recompressed: their EXIF orientation is read (`jpegOrientation`) and applied with the image's `cm` matrix (`orientationMatrix`), which handles flips too. PNGs are embedded as-is (pdf-lib re-deflates them losslessly). Anything else, or a PNG/JPEG pdf-lib can't parse, is decoded by the webview through an `<img>` and a canvas (which applies HEIC/TIFF orientation) and embedded as PNG if any pixel is transparent, otherwise JPEG at 0.92. Big photos aren't downsampled.
- **Page edit timing.** `usePageEdits` keeps per-tab state: a queue (edits run one at a time), the `pending` version (shown but not yet loaded by pdf.js; the next edit starts from it), a `generation` counter, and up to 20 earlier versions, capped at 256 MB in total (`trimHistory`). Commands capture the generation when issued and are dropped if another edit landed first, because their page indices refer to the old version. History belongs to one `source` object: if anything else replaces the tab's source (an outside change reloading the tab), the history is cleared, and an edit whose baseline changed while it was computing is cancelled. Save and moving a tab to another window first `await settled(tabId)`. Save only clears `carriedChanges` if the source it saved is still the tab's source. If pdf.js can't open an edited version, `documentFailed` restores the previous one instead of closing the tab. Undo and Redo are routed by `routeStep`: Undo goes to pdf.js while pdf.js has something to undo (`viewer.editHistory()`, from pdf.js's `editingstateschanged` event, so it survives Save), otherwise to page history, except after the user typed into a form field since this version loaded (`changed`, set by `input`/`change` events inside the annotation layer; typing isn't on pdf.js's undo stack, and page undo would take the typed values with it). Don't use `annotationStorage` modification for this: pdf.js writes to it while rendering radio buttons. Redo goes to pdf.js while pdf.js has something to redo; if markup or typing sits on top of the current version, page redo is cleared instead, because those versions predate it. While an edit is queued or a version is loading, Undo and Redo are queued behind it instead of going to pdf.js. `documentLoaded`/`documentFailed` get the `source` that finished loading and ignore stale ones, so a quick Undo can't clear the wait for a newer version. Selection lives in `DocumentTab` and only counts while it includes the current page (`followCurrentPage`), so scrolling away quietly drops it; commands act on the selection or else the current page. Dragging to the same spot is a no-op (`changesDocument`). Thumbnail drag-to-reorder is pointer based like tab dragging. Dropping PDFs or images on a visible sidebar inserts them at the drop line (`src/lib/dropTarget.ts`, marked with `data-drop-*` attributes React doesn't manage); dropping anywhere else opens them as before. The thumbnail context menu is a native popup (`showContextMenu`).
- **File access.** The webview can only read or write paths Rust handed out: files picked in Rust's dialogs (`pick_pdf`, `pick_document` for Open, which takes PDFs and Markdown, `pick_pdfs`, `pick_image`, `pick_images`, `pick_save_path`, `pick_markdown_save_path`, `pick_image_save_path`), dropped on a window, opened from Finder or the command line, or in recent files. `files.rs` keeps that allowlist (canonical paths) and `read_pdf` / `read_markdown` / `read_image` / `write_pdf` / `write_markdown` / `record_recent_file` check it, so a compromised page can't read arbitrary files. Each command also checks the extension (`is_pdf`, `is_markdown`, `is_image`), so a Markdown path never reaches `write_pdf` or the reverse. Files reached from a Markdown link go in `LinkedPaths` instead, a read-only allowlist (reads and stamps only), and images a Markdown file shows are read through `read_linked_image` without being allowed at all; see Markdown tabs. Folders picked with `pick_folder` go in a separate folder allowlist; `write_image` writes only `.png`/`.jpg`/`.jpeg` files, either to an allowed path or to a plain file name (no separators, `.`, or `..`) directly inside an allowed folder, and `existing_files` only answers for allowed folders. `write_pdf` never writes images and `write_image` never writes PDFs. Don't call the dialog plugin's `open`/`save` from JS for files; add a Rust command that allows the result. File IPC commands are `async` so large reads and writes don't block the main thread (sync commands run on it). The CSP lives in `tauri.conf.json`; `devCsp` is `null`, so `pnpm tauri dev` doesn't enforce it. Check CSP changes with a `pnpm tauri build` app.
- **Quitting.** Quit is a custom command (⌘Q), not the predefined item, because the predefined one terminates without any chance to ask. It reports this window's documents (finishing in-progress edits first) and calls `request_quit`, which exits right away or shows one native "Discard and Quit" alert listing every unsaved document across windows. Quitting from the Dock or logging out still skips the prompt: tao doesn't implement `applicationShouldTerminate`.
- **Dark pages.** The default ("Keep images") applies `invert(0.92) hue-rotate(180deg)` to `.canvasWrapper` and the editor layer, then draws each image's original pixels into an unfiltered overlay canvas (`.image-restore`). Image rectangles come from pdf.js's image tracker (`imagesRightClickMinSize: 0`) and are rotated by `src/lib/imageRegions.ts`. pdf.js's own `pageColors` high-contrast mode recolors images too, so it isn't used. `enableDetailCanvas` stays off: pdf.js draws the detail canvas inside `.canvasWrapper`, under the `.image-restore` overlay, and `restoreImages` copies image pixels from the base canvas (it skips detail renders), so at high zoom images would show at the base canvas's lower resolution on top of the sharp detail render. Turning it on means restoring images from the detail canvas too, at its offset.
- **Fit width / fit page on resize.** `usePdfViewer` re-applies preset zooms when the viewer's *border-box* size changes. Don't observe the content box: with always-visible scrollbars the scrollbar appearing narrows the content box, the page re-fits smaller, the scrollbar disappears, and the page loops forever (it shakes and pins a CPU). `.viewer-container` also uses `scrollbar-gutter: stable`.
- **Recent files.** Rust owns the list (`~/Library/Application Support/com.ry4nolson.clumsy/recent-files.json`, max 20, menu shows 10) so the native menu works before the webview loads. The frontend records a path after a successful load or a Save As, and listens for `recent-files-changed`.
- **Default PDF and Markdown app.** `default_app.rs` calls `LSCopyDefaultRoleHandlerForContentType` / `LSSetDefaultRoleHandlerForContentType` for `com.adobe.pdf` (what `duti` uses), or `net.daringfireball.markdown` for Make Clumsy the Default Markdown App (macOS declares that UTI itself; JS passes `"pdf"` or `"markdown"`, never a raw UTI). Only offered when running from an installed `.app`; dev builds aren't registered bundles. Only PDFs get the launch prompt.
- **Scroll and spread modes.** `viewer.scrollMode`/`spreadMode` reset on every `setDocument`, so they're applied in `pagesinit` before the zoom and location, from the tab's `ViewState` if it has one, otherwise the last choice (`clumsy.scrollMode`/`clumsy.spreadMode`, written only when the user picks a mode). They live in `ViewState`, so they survive tab moves, Reopen Closed Tab, outside-change reloads, and page edits. The Document Map lays pages out in rows (`pageRows`: pages whose boxes overlap vertically share a row), which covers spreads and wrapped scrolling. `MIN_PAGE_WIDTH` applies to each page, not the row. In wrapped scrolling the pane stays at `MAP_MAX_WIDTH` and centers its content: how many pages fit in a row depends on the viewer's width, so a pane that followed the layout's width would loop with the viewer (the same shake as fit width). Horizontal and page scrolling hide it, disable its menu item, hide it from the Command Palette, and ignore ⌥⌘B (`documentMapAvailable`), because the map follows vertical scroll. Next/Previous Page and the Space tap use pdf.js's `nextPage`/`previousPage`, which step by spread. `scrollLocation` reports the first page of a row, so linked scrolling follows the left page of a spread. Linked scrolling in a comparison is skipped while either side scrolls horizontally or by page (`CompareView.linkable`), and Next/Previous Change first sets the current page in those modes so `revealRect` has a laid-out page to scroll to.
- **Back and forward.** pdf.js's `PDFHistory` drives `window.history` and assumes one document per page, so each viewer keeps its own stack (`src/lib/navHistory.ts`, at most 50 stops) and plugs an adapter into `linkService.setHistory`: `pushCurrentPosition` records the current `updateviewarea` location before link and outline jumps, and the `GoBack`/`GoForward` named actions step it. Go to Page, first/last page, the palette's `:page`, the first find of a search and every Find Next/Previous, and comparison change jumps record explicitly (`recordStop`, `goToPage(page, true)`); ordinary scrolling and Next/Previous Page don't. Stepping pushes the current spot onto the other stack and scrolls with an XYZ destination, so it survives zoom changes. The stack is part of `ViewState`; page edits remap its pages with `pageAfterEdit` (`remapStops`). A jump updates the stored location right away, so two quick Back presses don't both start from the same spot. Mouse buttons 3 and 4 also step it; trackpad swipes don't (WKWebView's swipe gesture is its own back/forward navigation).
- **Opening a document's own view.** On a fresh open (no `ViewState`, and the path isn't in recent files yet, so only the first time a file is opened) `DocumentTab` reads `getOpenAction` (a `Map` in pdf.js 6), `getPageMode`, and `getPageLayout`. `documentView` in `src/lib/viewModes.ts` maps them: `UseOutlines`/`UseThumbs` open the sidebar on Outline/Pages, and `SinglePage`, `OneColumn`, `TwoColumnLeft/Right`, `TwoPageLeft/Right` become scroll and spread modes. The open action's destination is scrolled to without recording a history stop. Restores always keep the saved view.
- **Page labels.** `getPageLabels()` is loaded on every document load and handed to `viewer.setPageLabels` once pages exist; labels that are just "1", "2", … are treated as none. The page box shows the label with "(n of N)", and `pageFromInput` takes an exact label, then a case-insensitive one, then a number.
- **Hand tool and Space.** `src/lib/handTool.ts` pans the container from a capture-phase `pointerdown`, so it also works over the editor layers without switching pdf.js's editor mode. Tools > Hand sets the editor mode to none and turns it on; holding Space turns it on until release from any tool (`holdHand`), except in text fields, form fields, free text editors, and buttons (`wantsSpace`). A tap of Space without a drag scrolls a screen (Shift goes back), since the keydown is prevented.
- **Editor options.** pdf.js applies `switchannotationeditorparams` to the selected editors when there are any, otherwise to the class defaults, which are static and shared by every viewer in the window. The toolbar shows the selected editor's values (from `annotationeditorparamschanged`) or the remembered ones (`clumsy.editorParams`), and only remembers changes made with nothing selected. Remembered values are pushed whenever an editor mode turns on with nothing selected; pdf.js fires the mode event after it selects a double-clicked editor, which is why the push checks the selection. `HIGHLIGHT_FREE` isn't settable: pdf.js draws a freehand highlight whenever a highlight drag starts off text, so only its thickness is offered.
- **Find.** `PatternFindController` runs regular expressions against pdf.js's page text, which is NFD-normalized. Unless Match Diacritics is on, combining marks (except the ones pdf.js keeps, such as viramas) are stripped from both the pattern and the page text, matched, and mapped back so a match covers its accents. With it on, the pattern is NFD-normalized and matches that would end before a mark are dropped.
- **Caret browsing.** WebKit draws no caret in non-editable text, so `src/lib/caretBrowsing.ts` draws one (`.caret-mark`) at the selection's focus and handles the keys itself: Left/Right through `Selection.modify` (⌥ by word), Up/Down by finding the nearest text-layer box on the next line (`nextLine` in `src/lib/caretLines.ts`, continuing to the next page) and the character offset under the caret's x, Home/End to the ends of the line's boxes. Shift extends. Keys inside the annotation and editor layers (a selected drawing being nudged) are left to pdf.js. It's on per window (`clumsy.caretBrowsing`) and only in the focused pane's active tab, so turning it on doesn't move a selection in another pane.
- **Commands, shortcuts, and menus.** `src/lib/commands.ts` is the single source of truth: every command's id, label, menu, and key combos. The same table builds the native menu bar (`src/lib/menu.ts`, via Tauri's JS menu API, so the menu shows each shortcut), resolves keyboard shortcuts in `App.tsx`, renders the Keyboard Shortcuts sheet (⌘K or ⌘/), and fills the Command Palette (⇧⌘P). Every path ends in `runCommand(id)` in `App.tsx`. The layout follows VS Code's defaults where a PDF viewer has an equivalent (⌘B sidebar, ⇧⌘E thumbnails, ⇧⌘O outline, ⌘N new tab, ⇧⌘N new window, ⌘P Go to File, ⌃G Go to Page, ⌘↑/⌘↓ first/last page, ⇧⌘T reopen closed tab, ⌥⌘S Save All); keep it that way when adding commands. `⌘1`–`⌘8` stay as Show Tab N, not focus pane. Go Back/Forward use VS Code's macOS keys (⌃- / ⌃⇧-); `ctrl` combos only exist on macOS, so other platforms will need their own (VS Code uses Alt+←/→). Function keys (F7) are menu accelerators even without a modifier, since they never type text. To add a command: add it to the table, place it in `menuLayout` if it belongs in a menu (the tests check every menu command is placed exactly once and no combo is used twice), and handle it in `runCommand`. Combos use physical keys (`event.code`), so ⌥ shortcuts work even though Option changes the typed character. Plain-letter combos (`h`, `n`, `Home`) are ignored while typing and never become menu accelerators, because a native accelerator swallows the key everywhere, including text fields. Combos that move the caret (`movesCaret`: arrows, Home, End with no modifier, ⌘, or ⌥, plus ⇧) are also ignored by the keydown router while typing; ⌘↑/⌘↓ are still menu accelerators, so when one comes from the native menu (`runCommand(id, true)`) while a field with a caret has focus (`hasCaret`), it moves that caret to the start or end (`moveCaretToEdge`) instead of changing pages. A click on the menu item does the same, since Tauri can't tell it from the accelerator; the palette always changes pages. The keydown router skips Escape inside an open `<dialog>` and ignores IME composition keys. Commands that only work with a split set `needsSplit` (disabled in the menu, hidden from the palette). Scroll and spread modes are check items driven by `checkedCommands` in `menu.ts`, one checked per group like a radio. Native check items toggle themselves on click, so clicking the already-checked mode would uncheck it with no state change to redraw it; their action re-checks the clicked item. Typing `:` and a page number or label in the Command Palette or Go to File offers a single "Go to page" item (`pageJumpItem`). The Command Palette lists every menu command available right now; Go to File (⌘P) lists this window's open tabs and then recent files. Both are one in-window modal `<dialog>` (`QuickPick`) with a fuzzy matcher (`src/lib/fuzzy.ts`). Closing it blurs its input before running the picked command: WebKit leaves focus on an input inside a closed `<dialog>`, which made palette Undo/Redo act on the search field. Closing a tab that has a path remembers it and its view (page, zoom, scroll) for Reopen Closed Tab, per window, up to 20. Native menu accelerators win over the webview's keydown, which is why Undo/Redo are custom items that route to the focused text field or to pdf.js's `editingaction` event; the predefined Undo would never reach pdf.js. Document commands set `needsDocument` and are disabled in the menu when the active tab has no PDF. Those that also make sense for a Markdown tab add `markdown: true`, and Markdown-only commands (Markdown Source) set `needsMarkdown`; `documentAvailable` decides all three for the menu, the palette, and `runCommand`. The Rust side no longer builds menus.
- **Windows and dialogs.** Document windows are the only Tauri windows. About (with its What's New and Licenses tabs) and Keyboard Shortcuts are in-window `<dialog>` sheets in each document window (`AboutDialog`, `ShortcutsDialog`), held as one `infoSheet` state in `App.tsx`, so only one shows at a time. ⌘K toggles Shortcuts; Esc, Done, Close Tab, and Close Window close whichever is open before doing anything else. Rust and `documentWindows.ts` treat only `main` and `doc-*` as windows; new window labels must be added to `capabilities/default.json`. Questions with only buttons use native alerts (`@tauri-apps/plugin-dialog`, see `src/lib/defaultAppPrompt.ts`). The password, signature, and export prompts need inputs, so they're in-window `<dialog>`s styled as sheets (`.dialog.sheet`), like About and Shortcuts.
- **Title bar.** The window uses `titleBarStyle: Overlay` with `hiddenTitle`; the toolbar pads left for the traffic lights (except in fullscreen) and toolbar groups carry `data-tauri-drag-region`.
- **Third-party licenses.** `pnpm build` (and so every release) runs `scripts/third-party-licenses.mjs`, which collects license texts for the npm packages the UI bundles (production `dependencies`, walked transitively) and the Rust crates compiled into the binary (`cargo metadata`, normal dependencies only). For "A OR B" licenses it uses MIT when offered. Crates that ship without a license file get the shared Apache/MPL text or an MIT/BSD template with the crate's authors. Identical texts are listed once. The About sheet shows the result under Licenses. New dependencies are picked up automatically; check the "without a bundled license file" section of the output if a new license type appears.
- **Updates.** Two halves. Finding out about a release and showing its notes is still the GitHub releases API (`src/lib/updates.ts`, `useUpdatePrompt` in `main` only, every 6 hours and on focus; About > Check for updates in any window), because it can list every release since the running one. Installing goes through `tauri-plugin-updater`, called only from Rust: `install_update` (`src-tauri/src/updates.rs`) checks `latest.json` on the latest GitHub release, downloads `Clumsy.app.tar.gz` with progress over a `Channel`, verifies its minisign signature against `plugins.updater.pubkey`, and swaps the `.app` bundle in place (it asks for an admin password through AppleScript when the bundle isn't writable). `requireSignedVersion` is on, so the signature must name the version the manifest announces, which stops a replayed old release. The plugin's own JS commands aren't in the capabilities; the webview can only ask Rust to install whatever the configured endpoint offers. It refuses outside an installed `.app` (dev builds) and from a translocated copy (run from Downloads or the disk image), and the UI falls back to Download, which opens the release page. One install runs at a time across windows, requests time out after 10 minutes, and a version already installed in this process isn't downloaded again. Later and Esc close the Update sheet while a download runs (About keeps showing its progress); a failure offers Try Again and Download. The running process keeps the old version until Restart Now, which restarts with the session kept (below) through `AppHandle::restart`, which relaunches the bundle through LaunchServices. `useUpdateInstall` holds the install state per window, shared by the Update sheet and About.
- **Restart sessions.** Restart Now (`request_restart`, `src-tauri/src/session.rs`) emits `capture-session` to every document window and waits up to 30 seconds for each to answer `report_session`. `useRestartSession` captures a window with `captureTab` (shared with moving tabs between windows, so pending page edits settle first): saved files go by path and view state, while unsaved or pathless tabs bake their markup into bytes through the transfer stash, exactly like a tab move, so they come back with `carriedChanges` and lose only their undo history. Panes keep their order, sizes, active tab, and focus; windows keep their bounds, and the last focused window is focused again. Rust only keeps paths the window was actually given (`AllowedPaths`, or `LinkedPaths` as read-only, which stays read-only after the restart), so a page can't use a restart to widen its file access. When every window has answered, Rust writes `restart-session/` (0700) in app data and restarts; the next launch reads it, deletes it, restashes the bytes, allowlists the paths, and skips the command-line files the relaunch repeats. `main` opens one window per extra saved window (`?restore=N`) and each takes its own entry once (`take_restored_window`). If a window fails to capture or times out, or writing fails, it falls back to `confirm_quit` with `restart: true`, the old "Discard and Restart" alert. A tab that can't be reopened is skipped with one error listing its name. Comparisons, find, and sidebar panels aren't kept. Quitting doesn't save a session.
- **Version** shown in the app comes from `tauri.conf.json` at build time (`__APP_VERSION__` in `vite.config.ts`). CI runs `scripts/set-version.mjs` so `package.json`, `tauri.conf.json`, and `Cargo.toml`/`Cargo.lock` all match the release, then commits them with the stamped changelog.

## Releases

Every push to `main` builds, signs, notarizes, and publishes a GitHub release (`.github/workflows/release.yml`). Pull requests run `ci.yml` instead.

- **Versioning** (`scripts/next-version.mjs`): the bump comes from the changelog, so nobody picks version numbers. If `[Unreleased]` has an entry under `### Added`, the release bumps the minor of the latest `vX.Y.Z` tag (0.4.2 → 0.5.0); otherwise it bumps the patch (0.5.0 → 0.5.1). Feature branches and parallel sessions never edit version numbers: they only add entries under the right heading, and whatever has landed on `main` when the release runs decides the bump. Use `### Added` for new capabilities (commands, menu items, file formats, tools), not for improvements to existing ones, which go under `### Changed`. Major versions are manual: set `version` in `src-tauri/tauri.conf.json` (for example `1.0.0`); a version there that's ahead of the latest tag is released exactly, and later pushes continue from it. Don't hand-edit `package.json` or `Cargo.toml` for releases — the workflow keeps them in sync.
- **Changelog**: add user-facing changes under `## [Unreleased]` in `CHANGELOG.md` (Keep a Changelog sections: Added / Changed / Fixed / Removed; `**bold**` renders in the app). On release, the workflow moves those entries under `## [x.y.z] - date`, builds with the stamped file so What's New is correct, uses that section as the release notes, then commits the changelog and version files back to `main` as `Release vx.y.z`. If `[Unreleased]` is empty, the notes list commit subjects instead, but the version files are still committed.
- **If you've edited `CHANGELOG.md` locally while a release ran**, the pull can silently merge your new entries into the just-stamped version section. Check that they're still under `[Unreleased]` after pulling.
- **After every release `origin/main` is one commit ahead** (the version + changelog commit). Run `git pull --rebase` before pushing again, or set `git config pull.rebase true`. Pushes made with the workflow's `GITHUB_TOKEN` don't trigger new workflow runs, so there's no release loop.
- Releases run one at a time (`concurrency: release`). Pushes touching only `README.md`, `AGENTS.md`, `CLAUDE.md`, or `docs/` don't release. The workflow can also be run manually from the Actions tab.
- Assets are `Clumsy.dmg` and `Clumsy.zip`: universal (Apple Silicon + Intel), Developer ID signed, notarized, and stapled.

Team ID `M3C8F32WA5`; identity `Developer ID Application: Texas Beard Company LLC (M3C8F32WA5)`.

Updates are signed separately with a Tauri (minisign) key: `TAURI_SIGNING_PRIVATE_KEY` (the contents of `~/.tauri/clumsy-updater.key`) and optionally `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`; the public half is `plugins.updater.pubkey` in `tauri.conf.json`. After notarizing and stapling, the workflow tars the stapled `.app` into `Clumsy.app.tar.gz` (`COPYFILE_DISABLE=1`, the bundle at the archive root), signs it with `tauri signer sign --app-version`, and `scripts/update-manifest.mjs` writes `latest.json` (the same universal archive for `darwin-aarch64` and `darwin-x86_64`). - The exported certificate lives at `~/Developer/Certificates-duti.p12` (also `Certificates.p12`). Check a password with `/usr/bin/openssl pkcs12 -in <file> -nokeys -clcerts | /usr/bin/openssl x509 -noout -subject`. Use macOS's LibreSSL; Homebrew's OpenSSL 3 rejects Keychain's legacy encryption and looks like a wrong password.
- Notarization failing with HTTP 403 "A required agreement is missing or has expired" means the account holder must accept an updated agreement at developer.apple.com/account; nothing in the repo is wrong. Rerun with `gh run rerun <id> --failed`.

## Conventions

- Never commit test documents. `public/` is copied into the app bundle, and `public/*.pdf` is git-ignored for that reason; keep sample PDFs outside the repo. Review `git status` for new files before every commit instead of blindly staging everything.

- Match the existing style: no code comments unless the logic truly needs one, self-explanatory names, small pure helpers in `src/lib` with vitest coverage.
- Keep source files under 500 lines. When one grows past that, split it along a real seam (a hook, a component, a pure helper in `src/lib`) rather than arbitrarily.
- Global form-control resets use `:where(:is(button, input, select):not(.pdfViewer *))` on purpose: zero specificity so component classes win, and pdf.js's own controls (whose layers set huge font sizes) are left alone.
- pdf.js 6 API notes: `PDFDocumentProxy.destroy()` is gone (use `loadingTask.destroy()`); `page.render({ canvas, viewport })`; editor modes are set with `viewer.annotationEditorMode = { mode }`; default colors go through the `switchannotationeditorparams` event.
- Typecheck, test, clippy, and Rust tests must pass; the release workflow runs all of them before building.
- Commit messages: short imperative subject describing the change.
